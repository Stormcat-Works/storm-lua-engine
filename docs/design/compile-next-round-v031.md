# v0.3.1 コンパイル全経路・追加性能ラウンド

2026-10-04。前回の全経路改善（実装`1f9d58e`、記録`94de474`）を固定した比較元とする。Mapの追加倍率だけでなく、MapなしとMapあり双方の絶対時間を短縮する。最大1.2倍、できれば1.1倍の目標は維持し、通常経路を遅くする操作・mapを後で生成する操作・精度の削減で満たさない。

## 今回調べる仕事

1. **構文解析のトークン所有。** 既存の字句ツールは文字列を借用するが、Parserは全tokenを個別Stringとして保持し、記号を消費するときも複製している。入力を一度保持し、tokenは範囲・種類・位置だけを持つ内部表現を検討する。公開Parserの所有権・位置・エラー・AST順を変えない。
2. **共通effect解析の繰り返し処理。** 同じ組込みrootの文字列生成、全binding配列のfixpoint走査などを測る。同じ順序と収束条件を維持し、実際に必要な情報だけを再利用する。可変のpublic summaries/stable_readsに対する古いcacheは作らない。
3. **出力とマップの境界。** 完成した値の小さなfieldごとのJS往復と、map設定を中間JSONオブジェクトへ展開する費用を確認する。通常の返却型と非有限数・負のゼロ・欠落/nullableの契約を維持する。巨大なmap文字列を無用にもう一度JSONの文字列へ包む設計は避ける。
4. **元位置とマップ整形。** 並んだ座標で同じ原文の走査・検索を繰り返す部分を確認する。出力のcanonical bytes・指紋と全ての詳細情報は旧方式との比較を必須にする。

## 比較・採否

固定22入力×2経路（小入力・空・Unicode・property・字句短縮・巨大描画/制御）と、実コーパスの広い比較を併用する。lint/analyze、通常とLifeBoatのlink/minify、Workerと配布SDKも対象。実装単位の回帰テスト後にWASMで同条件のbefore/afterを測る。単発全体走査と反復部分集合を混ぜず、小差・悪化・失敗も保存する。

差分の分母は常に同じ変更後のMapなし。比率・絶対差・総時間を別々に出す。有限の測定を全入力/全CPUの保証と表現しない。無効時の回帰が再現する場合は原因を調べ、不採用または修正する。

生成Lua、diagnostics、検索/候補順・同点判定、詳細map全JSON（producer/integrity以外）、原文位置と理由・関係・文脈・除去記録を比較する。全240条件、target未達、新旧reader/Worker、Native/SDK/WASM/3ブラウザーを検証する。

`feat/minify-performance-v0.3.1`で意味のある単位ごとにcommitし、結果は本リポの検証文書へ保存する。push・main/release更新・publishは行わない。私有Lua原文は公開ファイルに追加しない。汎用永続cacheや新しい性能オプションは、今回の実測を越えて投機的に導入しない。
