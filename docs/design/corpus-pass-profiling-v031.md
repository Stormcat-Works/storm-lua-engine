# v0.3.1 実Luaコーパスによる最適化パスの費用・使用頻度調査

2026-10-03。短縮アルゴリズムをさらに変更する前に、Storm Minが保持する実Luaコーパスを使って改善先を選ぶ。既存のv0.3.1性能改善を含むコードを固定し、調査中は最適化の意味論・探索順・生成結果を変更しない。

## 対象

Storm Minの保存済みreal-world corpus（2026-09-25、commit `17af9263092aeee7a209180bd0521f3e03fe1382`）にある全4,155固有Lua。原文11,818,299 bytes、最小0 bytes、最大605,363 bytes、中央値2,059 bytes。全原文のSHA-256をファイルIDと照合する。過去のadmitted一覧だけを全体と呼ばず、不成功・空・vehicle用途外を含めて今回の成功/失敗を記録する。プロパティの5,966条件や同じ原文の13,737出現は独立スクリプトとして水増ししない。今回の主集計はruntime propertiesの1原文1票である。

原文は非公開コーパスに置いたまま読み取り専用で使う。公開Engineのソースや配布物にコピーしない。名前・コメント・原文・mapのsourcesContentを成果物として公開しない。個別結果はsource hashとサイズで識別する。

## 実行設定

- 主集計: `mode:smallest`、`numericMode:tolerant`、`searchMode:exhaustive`、`zeroCostNewlines:true`、`environment:game`、targetなし、runtime properties。全最適化パスを既定のまま使用。
- 比較: 同じスクリプト・設定でSource Map OFF/ON。ONには由来追跡と標準map・理由JSON生成を含む。外部からのvalidateは総短縮時間に混ぜない。
- 補助集計: `targetSize:8192`。原文返却は最適化パスを使った結果と区別する。多くの実ゲーム由来コードは既に上限内のため、この設定だけでパス優先度を決めない。
- 主な実行環境はNode上のWASM。利用するソースsnapshot・WASM hash・Node/OS・実行順・計測回数を記録。Nativeの値をWASMへ代用しない。
- 原文のLuaは実行しない。本調査はコンパイル費用の観測であり、ゲーム・差分VMによる意味的正しさの新しい認定ではない。

## 計測の定義

既存PassRecordの時間は採用経路の一部しか残らないため、それだけを全探索の費用にしない。測定用snapshotに計測hookを入れ、不採用候補も含む実呼び出しを集計する。製品の作業ツリーへ計測用依存やAPIを追加しない。

各パスについて、(1)呼び出された固有script数、(2)呼び出し回数、(3)既存のsize/detail判定で変更が記録された回数、(4)最終採用経路のPassRecordへ残ったscript数を区別する。(3)/(4)は同サイズ変換を網羅した意味的変更数とは限らず、記録がないことだけで完全なno-opとは断定しない。

パス時間は次を分ける。

- Inclusive: そのパス内で呼ぶ解析・印字・入れ子の変換も含む実時間。
- Attributed: 共通処理を呼び出し元パスへ帰属させ、別の入れ子パスの時間はそのパスへ分配した時間。費用ランキングに使う。パス間で二重計上しない。
- Self/exclusive: 計測した子処理を除いた時間。共通処理の横断ランキングに使う。

パース、名前解決、EffectAnalyzer構築、サイズ計測、名前割当、印字、構文再検証、候補準備/評価/選択、由来初期化/平坦化、標準map、詳細拡張/JSON、診断/結果整形を別に観測する。未計測の内訳は親のself時間に含め、架空の分類で埋めない。

## 統計

主な統計単位は「1スクリプトの1回の短縮処理中に、そのパス/処理へ費やした累積時間」。最小・最大・平均・中央値・P10・P90・速い下位10%の平均・遅い上位10%の平均をOFF/ONで別々に計算する。分位点の補間と端数の定義も結果へ記載する。

不使用0を含む全成功script母集団と、呼び出しがあったscriptのみの条件付き母集団を両方出す。失敗は別表にし、途中までの時間を成功結果と混ぜない。繰り返し計測を行った場合、source単位の中央値へ集約して、呼び出し数の多いscriptや同一scriptの反復を使用率の分母へ重ねない。

全体の重いパス、広く使われるパス、少数の外れ値へ集中するパス、map有効時に増える費用を別々に順位付けする。あるパスの高速化による上限改善は、単なる構成比に基づく推計であり、パス削除や他パスとの交互作用を測った値とは区別する。

## 信頼性確認

計測あり/なしの生成Lua・診断・検索統計・詳細map（producer/integrityのみ別扱い）の一致を確認する。全67パスにhookがあること、入れ子時間を重複計上していないこと、全体と内訳の収支、timer overheadを検査する。計測自身の負荷は無計測版との比較で示し、黙って補正・差し引きをしない。

長すぎる/失敗する入力は記録を残す。ハーネスの安全停止をコンパイラの時間制限と呼ばず、途中結果を成功扱いしない。すべての試行・除外と実行不能を明示する。

集計Markdown、全67パスのCSV/JSON、非パス処理のCSV、source単位の集計、計測方法・snapshot指紋・再実行スクリプトを保存する。今回の目的は改善先の選定であり、測定途中に最適化パスを変更したり、計測結果を根拠なく実装へ反映したりしない。commit/push/releaseは行わない。
