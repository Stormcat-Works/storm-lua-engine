# 最適化後ソースマップと探索処理の実装計画

記録日: 2026-09-30。P0/P1はv0.2.1としてnpm/GitHub/Playgroundへ公開済み。最適化後マップは専用branchのv0.3.0で開発し、公開・タグ作成は別の明示工程とする。

本書は今回合意した設計・実装順序を所有する。実装済み契約は[Source maps](../specs/source-maps.md)、現在地は[STATUS](../../STATUS.md)、検証結果は別のverification記録で区別する。

## 1. 目的と到達点

Storm Minから継承したminifyを、生成Luaから元ファイル・式・識別子へ辿れるLua-to-Luaコンパイラにする。最適化を弱めて位置を維持するのではなく、構造変換中に由来を保持する。最終文字列同士の差分・文字列一致から由来を推測しない。

初期の製品目標は、生成コードから原文への移動、原文から生成範囲への逆引き、実行環境が提供した位置のエラー表示への接続である。元の変数・消えたスタックフレーム・評価順序・一回ごとのループ反復を完全再現するデバッガーは別段階とする。

## 2. 合意した境界

| 処理 | 責務 |
| --- | --- |
| syntax | 原文スナップショット上のUTF-8バイト範囲、ASTと名前出現の位置、実際の出力を記録するprinter |
| analysis / lint | 原文を直接解析する診断に詳細範囲を返す。生成コードがなければ.mapの生成を必須にしない |
| build / link | コピー元と生成先の詳細な範囲を保持する。合成された接続コードと原文を区別し、元モジュールへ接続する |
| minify | 変換・複製・統合・削除・候補分岐に伴う由来の引き継ぎ、最終候補に一致する位置情報 |
| WASM / TS | 共通のRust実装を公開する境界。独自のLua意味論や別の由来推定を持たない |
| ホスト | ソース表示、双方向選択、実行chunk/成果物の識別、実停止可能位置へのbreakpoint接続 |

既存のArena ASTを維持し、ソースマップだけを理由にSSAや新しい汎用IRへ全面移行しない。既存crateの責務内に実装し、名称やLOCのためのcrate追加をしない。

## 3. 内部の由来情報

ASTの構造的等価性・サイズ評価と分離したサイドテーブルを基本とする。`NodeId`はArena内のIDであり、内容の直接置換、新規Arenaへのコピー、候補のcloneを位置の保存と同一視しない。ローカル宣言・引数など、独立ノードでない識別子の出現も最終的な追跡対象に含める。

由来は原文の`sourceId + [startByte, endByte)`を基準とし、必要に応じて主な由来・関連由来・変換種別を保持する。原文の直接対応、変換による対応、自動生成、追跡不足を区別する。精度を識別子・式・文・処理群として表し、文単位の帰属を文字単位の完全対応と説明しない。追跡不足を自動生成扱いで隠さない。

名前変更は各出現の由来を維持する。定数畳み込みは元の式に対応する。インライン化では定義内の位置と呼び出し位置を区別する。統合では複数の元範囲を保持し、元コードの削除には生成位置がないことを認める。補助デコーダー等は合成と明示する。

描画命令群をデータとループへ変換した場合、初期実装は処理群への帰属でよい。特定反復を元の一命令へ決めるには実行時の添字・データ要素との関係が別途必要である。

全パスの完全な履歴を無条件に保存しない。小さな由来IDと共有可能なテーブルを使い、原文や由来集合の候補ごとの大量複製を避ける。由来情報を候補採否や構造dedupのキーへ混入させない。

## 4. 出力と座標の契約

外部交換形式は既存と同じSource Map v3 JSONとする。`version: 3`、生成物名の`file`、元ファイル一覧の`sources`、任意の原文`sourcesContent`、元の名前の`names`、位置対応の`mappings`で構成する。`mappings`は行・列等の差分をBase64 VLQで符号化する。符号化は既存の`sourcemap::SourceMapBuilder`を再利用し、独自のVLQ実装を増やさない。標準の位置対応で表せない複数由来・変換関係・粒度は、同じ内部情報から生成する別添えの詳細情報を検討する。独立に二つのマップを推測生成しない。詳細情報の最終公開型はconsumerを接続する段階で確定する。

内部はUTF-8バイト範囲、JS consumer向けマップの列はUTF-16コード単位に変換する。行/列の0始まり・1始まりを境界で明示する。LF、CRLF、Unicode、サロゲートペア相当の文字、EOF、合成prefix/suffixを試験する。

Printerは実際に返す最終`code`に対して生成範囲を記録する。compactの評価用出力に付けたマップを、改行の異なる最終出力へ流用しない。元コードからリンク結果、リンク結果から最適化後コードへの対応を合成する際も、既存の行単位mapを経由して詳細範囲を失わない。

コードとマップは一つの成果物として保存する。原文スナップショット、設定、版、chunkの識別を保持し、コードの編集後に古いマップを使わない。生成コードhashだけでは異なる原文が同じ短縮結果になる場合を区別できない。`sourcesContent`の原文を公開するかはホストの明示的な配布判断とする。

## 5. 実行時デバッグと静的な位置対応を分ける

実行位置 → 生成Lua位置 → 元ソース位置のうち、ソースマップが担当するのは後半である。Luaの行情報から未知の列を作り出さない。1行へ圧縮されたコードのエラーが行しか返さない場合、複数候補を一つの元位置へ決めつけない。

静的なクリックには列があるので精密なmapを利用できる。デバッグ向け改行配置、VMの命令位置情報、実ゲームに埋め込む計測コードは通常のmap生成と別機能である。消えた変数の値・スコープ・実行順序は標準mapの`names`だけで復元できない。

## 6. 性能についての合意

**コンパイラに壁時計時間による探索打ち切りは存在しない。追加もしない。** 時間は観測値であり、候補選択・変換採否・探索の打ち切りに使わない。テストハーネスの外部watchdogとは明確に分ける。

`targetSize: 8192`が未達のとき、同一条件の全探索と実行時間が大きく離れる現状は最適化対象である。理想はほぼ同じ所要時間。目標探索が行った解析・変換・候補評価を全探索でやり直さず、同じ探索を継続する。目標が達成できる場合の早期終了は維持し、全探索側を遅くして比率を合わせたり、全探索の短縮品質を落としたりしない。

比較は同一入力・設定・機械・release成果物で行う。target指定なしの出力を基準に、未達時の生成物、tie-break、候補の重複実行、Native/WASMとWorker経路を検証する。目標達成時の候補が変わる場合は、出力文字数と処理時間を明示する。

最適化後マップの有無で、同じ探索条件・出力形式の生成Luaを変えない。必要な位置追跡コストは計測し、最終候補だけを標準JSONへ符号化する。

### 2026-09-30時点の観測

同じi5-13400F/KVM上の探索的な単発測定。WASMはNode上でありブラウザ/iPadの保証値ではない。

| 入力 | 文字数 | Native全探索 / 8192未達 | Node/WASM全探索 / 8192未達 |
| --- | ---: | ---: | ---: |
| 合成矩形4,096個 | 129,812 | 3.51秒 / 8.97秒 | 3.15秒 / 8.96秒 |
| 合成矩形8,192個 | 259,607 | 13.01秒 / 32.29秒 | 9.56秒 / 27.37秒 |
| 合成矩形16,384個 | 519,201 | 53.26秒 / 138.63秒 | 33.87秒 / 108.31秒 |

実用的な既存制御サンプル20,195文字はNode/WASM全探索2.94秒、8192目標0.33秒で達成した。「現実的には約4秒以内」はこの実用規模についての観測・目安として扱う。任意入力の保証上限ではなく、巨大な未達入力や未解決の大量テーブル代入条件まで4秒以内と扱わない。詳細な原ログ・非公開入力の情報はローカル検証領域に置き、公開リポジトリへ持ち込まない。

## 7. 実装順序と完了条件

- [x] P0: 未達targetと全探索の二重処理を排除する。全探索の出力維持、目標達成の早期終了、checkpoint/Worker継続、同一条件のNative/WASM再測定。
- [x] P1: リンク段の正確なバイト範囲と列対応を実装する。合成部分を明示的にunmappedにし、複数ファイル・Unicode・同一行境界を検証する。
- [x] P2: Parser/Printerと由来サイドテーブルを接続。原文snapshot・名前出現・式範囲を候補分岐、rollback、JSON/binary Workerへ渡し、最終候補に一致する内部GeneratedOriginsを返す。未対応変換はUnknownとして明示する。標準mapの製品APIはP4で扱う。
- [ ] P3: 最適化パスを単純置換、定数化、インライン化、共有化、描画データ化の順で監査・対応する。全パスを分類し、精度・未対応範囲を公開APIに偽りなく反映する。
- [ ] P4: `minify`/`build(minify:true)`のRust/WASM/TS成果物へ接続し、非短縮mapとの合成と公開型の整合性を検証する。
- [ ] P5: Playgroundで双方向位置選択、関連由来、自動生成/不明を表示し、エラー/停止位置に接続する。元変数の完全な復元とは分ける。

機械ゲートだけに頼らず、代表変換の原文・生成Lua・マップの対応を手動でも確認する。既存の解析診断、非短縮build、LifeBoatビルド、extended字句短縮、source loaderの契約を壊さない。公開・タグ・他製品の本番配備はこの着手の範囲外である。

## v0.3.0 P2/P3の現在地（2026-09-30）

Parserの全node/name span、Printerの生成byte範囲に、任意の由来テーブルを接続した。低レベル`CompileOptions.origin_source`を指定すると、通常探索・目標探索・字句短縮・元コードの早期返却・Worker継続の最終候補へ内部`GeneratedOrigins`が返る。コードと位置を別探索で再構成しない。[今回の検証](../verification/source-origin-propagation-030-20260930.md)。

P3は[全67パスの台帳](source-provenance-pass-audit.json)で管理する。19パスに由来伝播を追加したが、現段階ではすべてpartial扱い。残り48パスはpending。部分対応をパス全体の完了や全入力の追跡可能性と同一視しない。台帳のID集合はcanonical pass registryとテストで一致させる。

未対応の直接mutationは該当slotの由来を失効させる。新規nodeは明示的な由来がない限りUnknown。元のnode番号が同じ、印字が似ている、近くの親に位置がある、という理由で古い位置を復活させない。既知のhelper生成だけSyntheticと明示する。

P3の優先順は、局所式のコピー/置換とインライン化、名前/テーブルの再編、複数式の共通化、描画loop/data/辞書化。個別passの動作確認に加えて、複数passの連鎖で由来が消失・誤帰属しないことを検証する。単一のno-op fixtureを全変換の対応根拠にしない。

P4では標準Source Map v3と詳細由来の最終公開型を確定し、非短縮link範囲を通じて元moduleへ合成する。内部byte/外部UTF-16列、names、sourcesContent、Unknown/Syntheticの明示、code/map/元snapshotの成果物識別を一緒に扱う。現在の座標検証はfingerprintではない。高レベルRust/WASM/TSの`minify`にmapが付いたとは扱わない。

P5ではPlaygroundの双方向選択と関連由来・不明・自動生成表示、実runtimeの提供する生成位置へのエラー/停止対応を実装する。元変数や消失stack frameの完全復元は本版の必須条件に含めない。

npmの公開運用は[公開workflow](publication-workflow.md)に分離され、v0.2.1は公開とregistry再導入まで完了している。v0.3.0の開発作業で既公開tag/tarballを変更しない。
