# 検証記録: api-alias ローカル化へチャンクのローカル予算を組み込む（Codex 第2回指摘7系・api-alias 形）

- 実施: w4 第95サイクル（2026-10-31）
- 対象コミット: `74ec76e`
- 対象ファイル: `crates/storm-lua-minify/src/passes/api_aliases.rs` のみ
- 分岐元: 統合先端 `a830726`（第225ラウンド）

## 問題

api-alias 最適化のローカル化変種は、選択したキーごとにチャンク
ローカルを 1 つ宣言する（`local b = input.getNumber` 等）が、挿入
先であるチャンクの同時有効ローカル上限（200）を一切確認して
いなかった。チャンクが上限近傍にある場合、別名ローカルの挿入で
生成コードが読込不能になる（w6 第51サイクル v16-b8b:
root-local-globalization 無効化時に発現、対象モードのみ）。

w6 第53サイクルのトグル狩りで、跨パス合成の発現条件も具体化
された: チャンク 196 ローカル＋別名挿入 (+1)＋ゲート済みループ
合成 (+4)＝201（o10／s8 形、いずれも root-local-globalization
無効化）。ループ合成側のゲート（第214・215ラウンド）は自挿入分
を正しく会計しており、無会計の別名挿入が根だった。

## 修正

候補集合の選択（`run_with_analysis` の長さ比較）に実現可能性を
組み込む。ローカル化変種の場合に限り、共有ヘルパー
`max_active_locals` によるチャンクの同時有効ローカル最大値＋
選択キー数が上限 200 を超える候補集合を、長さ無限大として勝者に
なれないようにする（`make_candidate`）。会計は第208／212／213
ラウンドと同じ関数全体最大値方式。別名ローカルはチャンク全体で
生存するため、最大値＋キー数が正確な保守値になる。

- 空集合は常に実現可能: 上限超過の入力に対しても従来動作を保ち
  （このパスの責任で直す対象ではない）、選択は必ず読込可能か
  原文どおりの候補で終わる。開発中に、空集合まで無限大にすると
  上限超過入力で内部の整合性アサートが落ちることを確認し、この
  形に修正した。
- グローバル変種はローカルを宣言しないため対象外。

## 検証

- 単体テスト 4 件（api_aliases）: 上限ちょうど（チャンク最大 200）
  で選択が空になる／残り 1 枠でちょうど 1 件発火／十分下では従来
  どおり発火（対照）／上限超過の入力では追加しない。v16 形の
  生成ソース（c 本数 n に対しチャンク最大は n+5: 合算ローカル 1＋
  数値 for の 4 枠）で n=150／193／194／195／196 の実測により
  境界挙動を確認した。
- トグル diffexec（plain／opt／safe／target32／target128、
  対象トグル無効化）: ベース（`a830726`）では v16-b8b／o10／s8 が
  対象モードのみ乖離（読込不能）、ヘッドでは全て全構成一致。
  v16-b8a（199 で発火側）は前後とも一致。
- a5／l3 形（メソッド 194 引数、function-local-globalization
  無効化）について: w6 第53サイクルは api-alias 帰属としたが、
  本サイクルの検証では api-alias-optimization を追加無効化しても
  生成コードが不変であり、真因は S1／MR／SMC のメソッド暗黙
  self 過小評価（別ラウンドで修正・検証済み）へ再帰属した。
  根拠: LICM 自身のゲートは第218ラウンドの回帰テスト（a5 と
  同一形状）で発火しないことが証明済みで、勝者レイアウト
  （joint-api-local-licm）の共通段にあるメンバキャッシュ挿入が
  self 未計数で 201 本目になっていた。
