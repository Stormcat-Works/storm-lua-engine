# api-alias の追跡時再構築を勝者候補への由来移譲に変更し追跡コストを削減する（2026-10-27、未公開）

api-alias 最適化（`api-alias-optimization`）は、候補選定を由来なしの
コスト専用 AST で行い、追跡入力に対しては勝者をもう一度
`apply_alias_set` で再構築（replay）していた。勝者候補の値とノード番号は
replay と同一になるため、再構築をやめ、勝者候補へ由来だけを移譲する
方式に変更した。生成 Lua・候補選択・schema1 のマップ本体は維持する。
Map 比 1.2 の目標は未達のままであり、この変更はその達成を主張しない。

## 原因

追跡差の内訳切り分け（合成入力 dense-normal、計数アロケータ付き
ハーネス、11 反復中央値）では、api-alias パス単独の追跡差 19,680 回の
うち、最終 replay 分が約 9,547 回、後段の scope-renaming 分が約
10,133 回だった。replica プローブで純粋クローン 1 回分を測ると、
replay のコストは追跡側だけの上乗せではなくクローン 1 回分そのもの
（勝者候補の再構築）であることが判明した。replay 内の
`derive_from_clone` 自体は無コストで、コストはノード値の複製と
`resolve_builtin_reference` の名前 String 確保に分散していた。

## 変更

- `crates/storm-lua-syntax/src/node_arena.rs` に
  `NodeArena::attach_origins_like` を追加した。由来なしで構築済みの
  arena に対し、源のスナップショットを共有する空スロット付き由来
  テーブルを付与する。公開 API の追加のみで、既存シグネチャは変えて
  いない。
- `crates/storm-lua-minify/src/passes/api_aliases.rs` の追跡分岐を、
  勝者候補への由来移譲に置き換えた。
  - 置換ノードは `derive_from`（従来と同じ理由
    `api-alias-optimization`）、複製ノードは `derive_from_clone` で
    源スロットを共有する。
  - 置換判定は値比較で行う。複製は種類とシンボルを保ち、エイリアス名は
    `fresh` 保証の未使用名であるため、候補が Name で源が別構造または
    別シンボルの場合にちょうど置換と一致する。これにより移譲走査での
    `resolve_builtin_reference` の名前確保が不要になった。debug ビルド
    では両判定の一致を assert している。
  - 定義付き新ルートでは、新ルートにインラインされる本体 Block 自体が
    孤児になるが replay では由来が付いていたため、定義部分木の最小
    ノード ID−1 で本体 Block を特定して `derive_from_clone` する。
  - 新ルートの `derive_from` は、本体・定義スロット充填後に実行する。
    replay と同じ順序でないと、新ルートの detachment 走査が読む
    スロットが変わり dispositions が変わる。
  - 走査は反復＋バッファ再利用（`TransferBuffers`）で行う。再帰＋
    ノードごとの子 Vec 確保では、移譲が replay より高コストになった
    ためである。
- 候補選択・scope-renaming・生成コードには手を入れていない。

## 測定

合成入力は dense-normal（46,022 バイト）。VM 2 コア、計数アロケータ
付きハーネスで各条件 11 反復の中央値を測った。

| 測定 | 変更前 | 変更後 |
| --- | ---: | ---: |
| api-alias・追跡なし確保回数 | 115,530 回 | 115,530 回（不変） |
| api-alias・追跡あり確保回数 | 135,210 回 | 131,179 回 |
| api-alias・追跡差（確保回数） | 19,680 回 | 15,649 回（約 −20%） |
| api-alias・追跡なし確保バイト数 | 30,385,032 B | 30,385,032 B（不変） |
| api-alias・追跡あり確保バイト数 | 32,825,028 B | 31,911,820 B |
| api-alias・追跡差（確保バイト数） | 2,439,996 B | 1,526,788 B（約 −37%） |

追跡なし側が変更前後で完全に同一であることから、削減が追跡経路だけの
ものであることを確認した。saved=7127・コード長 13841・ノード数
6883→5940 は同一。時間差は負荷変動が大きく、時間改善は主張しない。

## 等価性の証拠

- `trial_provenance_tests` の 3 件が、新旧実装の AST・由来・理由
  スナップショット完全一致と生成由来一致を検証する（全登録パス入力、
  影・Unicode・不完全由来の edge ケース、空エイリアス集合と繰り返し
  メンバー候補を含む）。この変更の開発中に見つかった孤児本体 Block
  と detachment 順序の 2 件の不一致は、いずれもこのテストで検出し、
  修正後に全件通過した。
- 実コーパス全件比較の結果は下記のとおり（別途記録）。

## 実コーパス全件比較

StormMin の real-world コーパス（4,155 固有 Lua）を 開発ホスト2 上で
読み取り専用に使用し、base（統合先端 `d37691d`）と head を 4 条件
（default の Map なし／あり、std の Map なし／あり）で比較した。
コーパスの内容は本記録にも結果 TSV にも含まれていない（ファイル ID・
ハッシュ・集計値のみ）。検証用の一時ファイルは一時領域に置き、
完了後に削除済み。base / head の検証バイナリが異なるものであることも
SHA-256 で確認した（base `9d4f581b…`、head `acb16b27…`）。

- 両 TSV はバイト同一（SHA-256
  `acf6aa0f70ca3f52e25d87051b1360b6f2b8238618ebad4276e14bd909115741`）。
- 全条件で identical=4,155 件、hard・core・expl・missing すべて 0 件。
- 成功／失敗は全条件とも両側で成功 4,127 ファイル／失敗 28 ファイル
  で完全一致。生成コード・Map 中核・正規化済み Map 全体にも差分はない。

結論として、今回の変更は実コーパス全件に対して観測可能な変化を与えない。
由来移譲が replay と等価であることと整合する。
