# 候補J（関数ローカル・グローバル化が生成する巨大代入が Lua パーサ上限を超える）の修正 — 検証記録

対象: `crates/storm-lua-minify/src/passes/function_globalization.rs`
担当: w9 第64サイクル（第241〜252変更面への差分狩猟で発見。Codex 第3回 #11 の
ケース r3-11 の原形が、スカラ化ではなくグローバル化経由で発散していた）

## バグ

199個のローカルを持つ関数本体の宣言が、関数ローカル・グローバル化により
199ターゲットの単一代入文に変換され、生成コードが素の Lua で
ロードできなくなった:

```lua
local function f(t) local p0,p1,...,p198; return t.a+t.b end
return f({a=2,b=3})   -- 素: 正常終了 / 最適化: vm-error
-- 生成コードを素の Lua に読ませると:
-- syntax error: too many C levels (limit is 200) in function at line 1 near '='
```

第59再現スイートではこのケースは一致していた。スイートの実行器 c54exec は
プロジェクト VM（dialect 書換え経由）で実行するため、書換えが巨大代入を
救済して欠陥をマスクしていた。生成コードの妥当性は素の Lua バックエンドの
受理が基準である（第241ラウンド／第3回 #14 の先例どおり）ため、これは欠陥。

## 根本原因

Lua のパーサは代入文のターゲット列を再帰的に消費し、ターゲット1個あたり
概ね C レベル1を上限 200 に対して使う。包囲する関数も1段あたり概ね1を
使う（実測: トップレベル関数内では 199 ターゲットで失敗・198 で成功、
関数が1段深いと境界は 198 に下がる）。
`function_globalization` の書換えは、宣言の全 binding が対象のとき
`Local` 文をその場で `Assign` 文に変換するため、宣言の名前数がそのまま
単一代入のターゲット数になる。200 予算は関数本体ローカルの上限
（引数＋199）でほぼ使い切られており、変換に予算検査がなかった。

帰属: トグル二分で root-local-globalization と function-local-globalization の
両方を個別に無効化すると一致が回復する連鎖（root 側で関数がグローバル化
されてから本体ローカルが変換される）。スカラ化（第224の予算ゲート）は
無効化しても発散が残り、無関係であることを確認した。
root-local-globalization 自体はチャンクルート文だけを対象とし、
実測ではソース側上限の 200 ターゲットでもトップレベルでは受理されるため
対象外（深さが最小の位置でのみ変換される）。

## 修正

対象選択の all-or-none グルーピング（宣言単位で全 binding が適格な場合のみ
対象化）に、宣言の名前数の上限 `MAX_GLOBALIZED_DECLARATION_TARGETS = 150`
を追加した。上限を超える宣言の binding は対象に入らず、宣言はローカルの
まま残る。150 は実測境界（深さ1で199／深さ2で198）から約50レベルの
余裕を持たせた値で、現実的な入れ子深度では到達しない。150名を超える
単一宣言は Codex 生成のストレスケース以外に観測されていない。

## 検証

- 回帰テスト2件追加（160名宣言はローカルのまま残る／上限ちょうど
  150名は従来どおりグローバル化される）。上限を 1000 にする突然変異で
  前者だけが失敗することを確認した。
- 実地確認: 名前数 100〜200 × 深さ（関数内／二重入れ子／ループ内包）×
  root 使用形の境界ケース群と r3-11 原形が、修正後に全設定で一致。
- ワークスペーステスト 1,662 件全通過（候補Iの修正と合算）。
  clippy 警告集合はベースと同一、rustfmt 適合。
- Tier FULL（累積、FULL-VERIFY-TIP `79c0acf` から）: 全コーパス
  16,620 行・fallback 0、両側 SHA-256 `4a98d093…` でバイト一致
  （変更ファイル 0 件——上限を超える宣言は実コーパスに存在しない）。
