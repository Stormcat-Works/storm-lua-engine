# 検証記録: 候補S11（plain 糊付けラベル形の方言書換え破壊）

- 実施: w9 第73サイクル（2026-11-02）
- 対象コミット: 本記録の直前の修正コミット（分岐元 `34ce60a`＝FULL-VERIFY-TIP／第297ラウンド先端）
- 対象ファイル: `crates/storm-lua-vm/src/dialect.rs` のみ（回帰テスト 2 件を含む）
- ティア: FULL（VM のロード挙動が変わる正しさ修正）

## 問題

ブロック末尾ラベルへ同一ブロック内の goto が局所宣言を飛び越える合法
プログラム（第210ラウンドの方言規則で VM が受理する形）が、plain 経路
でのみ誤拒否された。w6 第78サイクルが確定した候補 S11。

## 根本原因（実測で特定）

plain プリンタはラベルを直前の文へ糊付けして出す
（例: `a=b::done::end`）。方言変換 (b) の goto 包みは、包み区間の開始
（`do `）とラベル直前（`end `）へキーワードを挿入するが、挿入位置の
直前バイトとの結合を考慮していなかった。糊付け形では:

- `a=b::done::end` → `a = bend ::done:: end`（`b` + `end` が識別子
  `bend` に融合し、関数本体が閉じず `'end' expected near <eof>`）
- `local y=9::cont::` → `local y=9end ::cont::`（`9` + `end` が不正数値
 となり `malformed number near '9e'`）

いずれも一時プローブ（`dialect.rs` へ一時追加し検証後に除去）で書換え
結果そのものを実測して確認した。空白のある形では従来どおり正しく包ま
れるため、欠陥は挿入部の区切り文字の欠如そのものである。

なお、plain 経路の拒否は第210ラウンドの検査によるものではない。検査
（PUC パーサのスコープエラー）は別経路であり、S11 の失敗はパース
レベルのエラーである。S10 族の plain 拒否の一部も、実はこの糊付け
欠陥によるものであった（下記「S10／S12 との関係」参照）。

## 修正

`crates/storm-lua-vm/src/dialect.rs` の (b) 包み挿入部で、挿入位置の
直前バイトが名前・数値の継続文字（英数字または `_`）の場合にスペース
を1つ挟む。改行は増やさないため行番号は保存される。空白のある従来形
では挿入結果はバイト同一（直前バイトが空白の場合はスペースを追加し
ない）。

## S10／S12 との関係（本サイクルの調査結論）

- S10 の未使用バリア形（gotoscope-min／fn／block／localfn／
  midblock）は、ソース直接の VM ロードでは第210ラウンドの方言包み
  によりもともと受理される。コンパイラが受理することも方言意味論と
  一致しており、PUC との差は第210ラウンドで承認された方言そのもの
  である。S10 の真の核は、使用バリア形（gotoscope-used、p6 形）で
  あり、こちらは後続のソース合法性ゲート（S10／S14 修正）で閉じる。
- S12（VM が未使用バリア形を受理すること）は、同じく第210ラウンド
  の方言規則そのものである。包みを狭めて PUC 並みにする変更は
  第210ラウンドの承認内容を覆すことになるため、本サイクルでは実施
  せず、ユーザー判断事項として親へ申し送る。S11 修正後の plain
  経路は、未使用バリア形を VM と同じく受理するようになる（従来の
  plain の拒否は糊付け欠陥によるものであった）。
- プリンタ側の区切り挿入（S11 修正要求の (ii)）は、VM 側の修正で
  糊付けテキストが正しく読めるようになったため実施しない。plain
  出力バイトの安定性を保つ判断である。
