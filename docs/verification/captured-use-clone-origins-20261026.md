# captured 単一使用ホイストのクローン由来共有による追跡コスト削減（2026-10-26、未公開）

captured 単一使用ホイスト（`captured-single-use-hoisting`）で、使用文の
複製と捕捉式の複製に対する由来付けを共有するよう変更した。生成 Lua・
候補選択・schema1 のマップ本体は維持する。Map 比 1.2 の目標は未達の
ままであり、この変更はその達成を主張しない。

## 原因

`NodeArena::derive_from` の高速経路は、対象ノードの値全体が源ノードと
等しい場合にのみ由来スロットを共有する。`replace_read` は使用文の木を
複製しながら、捕捉された名前の読みだけを捕捉式の複製で置き換えるため、
最初の置換以降は後続ノードの子 ID がずれ、値の等価性がほぼすべての
ノードで崩れる。結果として、変更のないクローンにもかかわらず低速の
書き換え経路（理由の生成・トークン／名前の保持判定・新規スロット確保）
が走っていた。これは API 別名パスと単一使用ローカルのシンクで
`derive_from_clone` が解消したのと同じ構造である。

## 変更

- `crates/storm-lua-minify/src/passes/captured_use.rs` のみ変更し、
  `clone_subtree` と `replace_read` の `derive_from` を
  `derive_from_clone` に置き換えた。置換された読みそのものは従来どおり
  `clone_subtree` で複製した上で `relate_from` で使用箇所との関係を
  記録する。`derive_from_clone` は種類が異なる場合や source snapshot
  を共有しない場合に従来の `derive_from` へ委譲するため、本物の置換は
  従来どおり書き換え理由を記録する。スロット共有後に `relate_from`
  が走る場合も、関係の記録はスロットをコピーしてから行うため、源の
  スロットが壊れることはない。
- この変更の適用範囲は captured 単一使用ホイストだけである。他のパスの
  クローン箇所は今回変更していない。`build_sum` のような新規合成ノード
  を作る箇所や、書き換えそのものを表す箇所は従来のままである。

## 測定

合成入力（500 個の `do` ブロック。各ブロックは捕捉 `a=123`、無関係文
`x=1`、使用文 `y={a,10,20,...,120}` からなる。使用文はテーブル式で
あるため移動可能であり、ブロックごとに 1 件のホイストが起きる）。
VM 2 コア。計数アロケータ付きハーネスで各条件 31 反復の中央値を測った。

| 測定 | 変更前 | 変更後 |
| --- | ---: | ---: |
| パス単体・追跡なし確保回数 | 35,048 回 | 35,048 回（不変） |
| パス単体・追跡あり確保回数 | 54,179 回 | 45,679 回 |
| パス単体・追跡あり確保バイト数 | 5,162,701 B | 4,592,701 B |
| パス単体・追跡差（確保回数） | 19,131 回 | 10,631 回 |
| パス単体・追跡差（確保バイト数） | 1,661,664 B | 1,091,664 B |

追跡なし側が変更前後で完全に同一であることから、削減が追跡経路だけの
ものであることを確認した。時間については、同じハーネスの追跡差が
約 2.36ms から約 1.58ms へ縮んだ一方で、単独パス測定の反復では変動が
大きく、時間改善としては主張しない。確保回数の削減が確実な効果である。

## 同一性

- パス単体の印字：上記合成入力 500 ブロックについて、stash による
  前後比較で印字全体の SHA-256 が一致し、ホイスト件数も変更前後とも
  500 件である。
- 公開コンパイル全体：捕捉と使用文の後にその結果を読む関数を持つ
  合成入力（`a=123 x=1 y={a,10,20,30,40,50}` と
  `function onTick() output.setNumber(1,y[1]) end`）を stash による
  前後比較で確認した。生成コードは SHA-256 一致（43 バイト）。勝者は
  変更前後とも `optimized:locals/none`。マップの mappings・names・
  sources・sourcesContent・version と、`x_storm` の compilation・
  constructs・contexts・dispositions・generated・mappings・origins・
  reasons・relations・schemaVersion・sources はすべて同一である。
  差が出たのは `x_storm.producer`（測定時の未コミット状態を示す
  dirty フラグ）と、それを覆う `integrity` のみである。この入力では
  `x_storm` の説明履歴そのものに差が出ていない。
- 実データの標準検証（コーパス全件比較）は、コミット後に別途実施し、
  作業記録に残す。
