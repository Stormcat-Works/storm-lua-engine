## 修正内容

通常経路:

- R01（minify、root_globals）: 二項演算子の被演算子読み取りについて、
  括弧で包まれた読み取り `(x)` も「書き込み後に読まれ得るローカル」と
  して大域化から除外する。Q01 修正の一般化として、被演算子の形に
  依らず除外判定が働くよう括弧層を剥がしてから名前判定する。従来の
  逆向きの期待値を置いていたテストは是正し、括弧付き形の回帰テストを
  追加した。
- R02〜R04（VM 方言、代入先評価時点モデル）: 多重代入では代入先参照
  （基底・キー）を右辺評価より前に固定する PUC 意味論を全形状で保存
  する。(R02) 同一文内の後の平名代入先と衝突する基底・キーは、衝突
  する代入先の直前で固定する「衝突固定」を導入し、19形状の差分
  プローブで PUC と全一致させた。(R03) 括弧付きキー `t[(k)]` を素の
  キーと同一視し、遅延読みする名前は括弧内側の名前でスナップショット
  する。(R04) repeat の until 条件式を本体フレームが有効なまま走査し、
  捕捉される本体ローカルを大域化しない。R210 の last-wins 値意味論は
  維持した。
- R05（VM 方言、一時変数予算）: for ループの内部ローカル（数値 for は
  制御変数＋3枠、generic for は宣言名＋3枠）を一時変数予算へ計数する
  （R306 の Q13 でフォールバック側へ入れた会計と一致）。予算超過時に
  書き換え対象の文は、書き換えず PUC 形のまま残すことでロード可能性
  を保存する。
- R06/R08（build、リンカのレジスタ予算）: レジストリ参照の字句的
  可視性を境界条件でも保つ。従来の大域退避分岐を廃し、レジストリを
  生成チャンク内の字句ローカルとして定義し、エントリ本体を関数で
  包む「ラップ形」を導入した。ラップ形ではレジストリが upvalue と
  なるためエントリフレームのローカル／レジスタを消費しない。移行
  条件は、エントリのローカル数 200 以上、またはチャンクピーク
  レジスタ見積もり（PUC 式のローカル＋一時値の上限見積もり）が 254
  以上。実測キャリブレーションでは、フレームはローカル数＋戻り値
  リスト長 ≤ 254 でロード可能であり、見積もり境界と一致する。
  ローカル `_ENV` 遮蔽下でも、253 個の戻り値を持つエントリでも、
  元がロード可能な入力は生成物もロード可能になった。
- R07（build、リンカの `_ENV` 隔離）: モジュールがエントリチャンクの
  可変 `_ENV` セルを共有しない。各モジュール定義とインライン展開を
  `do local _ENV = _ENV ... end` で包み、実大域環境へ束ね直す。包みは
  リンク対象集合（使用モジュール＋ambient）のいずれかが `_ENV` を
  再束縛する場合にのみ生成する。無条件に生成すると、生成物に現れる
  `_ENV` 識別子が minify の環境アクセス判定に触れて全プロジェクトが
  保守的縮小へ落ちる（製品回帰）ためであり、再束縛が無い場合は共有と
  隔離が観測上等価である。

フォールバック／条件限定:

- R09（load_legality）: 引数超過の早期 return で外側の歩行状態
  （active_locals 等）を復元せず、debug で減算溢れ panic していた。
  全ての出口経路で保存状態を復元し、ブロック巻き戻しにも
  saturating_sub の防御を入れた。通常エラーへ是正。debug／release
  両プロファイルで対照する回帰テストを両バックエンド構成に配置。
- R10（load_legality）: 末尾の連続ラベル列全体をブロック末尾ラベル
  として扱う（従来は最後の1つだけ）。列の先頭へのジャンプは、その間
  のローカルのスコープへ跳ぶことにならない。
- R11（文書）: フォールバック残差の記述へ、自前パーサの入れ子深さ
  上限（128）を追加した（英モジュール文書と和文 legality 文書の
  両方）。完全コンパイルは両バックエンドとも同入力を拒否するため
  出力の分岐はない。
- R12（深さガード）: 方言の書き換え本体を、大きなスタック（256MiB）
  を持つ専用ワーカースレッドで実行する。スポーン失敗時はインライン
  へフォールバックし、ワーカーの panic 時は原文をそのまま返す。
  パース深さ上限（1000）は変更しない。受け入れ条件「debug／release
  × 2MiB／8MiB の全組合せで Vm::execute と check_load_legality が
  異常終了しない」をドライバ行列16組合せで確認した。なお 499 重ねの
  関数入れ子は、参照側が PUC の C レベル上限（200）で、フォール
  バック側が入れ子上限で、それぞれ通常エラーとして拒否するのが
  正しい挙動である。

付随是正: 継承した `cargo xtask check` 違反を文言のみで解消した。

分類A監査のカテゴリ列挙に具体値（ホームパス等）を併記しており、

## 残件・観測事項

- R08 のレジスタ見積もりは上限見積もり（over-approximation）であり、
  実際のピークより大きく出る入力では不要にラップ形を選ぶことが
  ある。出力のロード可能性と意味は変わらないため許容する。境界の
  実測キャリブレーション（ローカル数＋戻り値長 ≤ 254）は見積もり
  境界と一致した。
- R05 の予算超過時の扱いは「文を書き換えず PUC 形で残す」であり、
  重複代入先のような形状では方言の R210 値意味論でなく PUC の
  first-wins が観測される。これは意図した縮退であり、回帰パック
  R05 のケース形状もこの境界に合わせて選んである。
- R07 の隔離生成は条件付き（リンク対象集合の `_ENV` 再束縛時のみ）。
  無条件生成が minify 側の環境アクセス判定へ与える影響は本文の
  とおり。将来 minify の判定が生成マーカーを区別できるようになれば
  無条件化を再検討できる。
- 本ラウンドの対象外: スカッシュ再構築・push・CI・公開工程
  （次段階）。STREAK／LAST-REVIEWED-TIP は変更していない。
