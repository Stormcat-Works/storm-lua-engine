# Codex 第3回指摘5（one-use function fusion の TailAssign 評価順序）の修正 — 検証記録

対象: `crates/storm-lua-minify/src/passes/inline_functions.rs`（末尾代入融合のゲート）
担当: w9 第62サイクル

## 指摘（Codex 第3回 #5）

```lua
t = {}
function f() t = {} return 1 end
t.x = f()            -- 素: t.x は nil（書込みは呼出し前の旧 t へ）
output.setNumber(1, t.x or -1)   -- 素: -1 / 最適化: 1
```

メンバーターゲットは右辺の呼出しより前に基底が特定される
（基底がグローバルなら一時領域へ読み出される）。ところが末尾
代入融合はキャリー本体を先に継いでから代入文を再発行するため、
基底の特定が本体の後になり、本体が基底を再束縛すると書込み先
が新しいテーブルへ移ってしまう。w6 第54サイクル項目3で、基底が
ローカル（レジスタ再読で一致）な形は root-local globalization
側の問題、本形は融合側の問題と切り分けられていた。

## 修正

融合の適用直前に `tail_assign_target_safe` ゲートを追加した。
メンバーターゲットを持つ末尾代入について、ターゲットが
「実体化される」部分（レジスタでない基底／自明でないキー）を
持ち、かつキャリー本体の書込みがその指す先を変え得る場合に
融合を見送る:

- 基底が包囲関数のレジスタ束縛への裸の名前で、キーがリテラル
  か同じくレジスタの裸名なら、その部分は保存時に再読される
  ため本体先行と一致する（融合可）。
- 実体化される部分については、本体内の束縛書込み（名前ター
  ゲット）がターゲットの読む束縛と重なる場合、本体内のメン
  バー書込みがターゲットの読むチェーンの接頭辞（自身を含む）
  を通る場合に不受理とする。チェーン分解には第244ラウンドの
  `decompose_chain` を共有する。
- 引数・ループ変数・外部由来のローカルをルートとするメンバー
  書込み、本体が生成した新鮮なストレージへの書込みと証明で
  きない書込みは「野生」として扱い、実体化部分がある限り
  不受理とする（引数経由の別名を解析しないための保守側）。
- 回帰テスト5件を追加（グローバル基底の再束縛で見送り、
  ローカル基底では継続、チェーン基底の置換で見送り、引数
  経由のメンバー書込みで見送り、書込みなしでは継続）。
