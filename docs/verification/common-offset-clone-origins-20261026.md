# common-offset 吸収のクローン由来共有による追跡コスト削減（2026-10-26、未公開）

common-offset 吸収（`common-offset-absorption`）で、オフセット式の
複製に対する由来付けを共有するよう変更した。生成 Lua・候補選択・
schema1 のマップ本体は維持する。Map 比 1.2 の目標は未達のままであり、
この変更はその達成を主張しない。

## 原因

`NodeArena::derive_from` の高速経路は、対象ノードの値全体が源ノードと
等しい場合にのみ由来スロットを共有する。`clone_subtree` は子を先に複製
してから親を積むため、子 ID がずれた内部ノードでは値の等価性が崩れ、
低速の書き換え経路（理由の生成・トークン／名前の保持判定・新規スロット
確保）が走っていた。これは API 別名パス・単一使用ローカルのシンク・
captured 単一使用ホイスト・immutable キャリア合成で
`derive_from_clone` が解消したのと同じ構造である。第9ラウンドでは
複製される項が大半リーフであるため効果が見込みにくいと判断したが、
内部ノードを含むオフセット項（積の積など）で効果を測れる入力を作り、
今回の適用を再評価した。

## 変更

- `crates/storm-lua-minify/src/passes/common_offsets.rs` のみ変更し、
  `clone_subtree` の `derive_from` を `derive_from_clone` に置き換えた。
  複製される式は純粋な複製であり、種類と識別子・リテラルの位置は源と
  同じで子 ID だけが異なるため、`derive_from_clone` の保証に合致する。
  種類が異なる場合や source snapshot を共有しない場合は従来の
  `derive_from` へ委譲する。
- 吸収の本体（残り項の組み立て・書き換え理由の記録・更新文の合成）は
  従来どおりであり、共有した源スロットが壊れることはない（関係の記録は
  スロットをコピーしてから行う）。
- 新規合成ノードを作る箇所や、書き換えそのものを表す箇所は従来のまま
  である。

## 測定

合成入力（`onTick` 内で、内部ノードを含むオフセット
`(p*2+q*3)*(r*4+s*5)` を持つ 4 要素のテーブル文と `b=0` による確定上書きを
40 組繰り返す 4,412 バイト。吸収 8 件、検討 144 件）。VM 2 コア。
計数アロケータ付きハーネスで各条件 31 反復の中央値を測った。

| 測定 | 変更前 | 変更後 |
| --- | ---: | ---: |
| パス単体・追跡なし確保回数 | 147,322 回 | 147,322 回（不変） |
| パス単体・追跡あり確保回数 | 157,878 回 | 153,846 回 |
| パス単体・追跡あり確保バイト数 | 46,490,206 B | 46,278,478 B |
| パス単体・追跡差（確保回数） | 10,556 回 | 6,524 回 |
| パス単体・追跡差（確保バイト数） | 806,592 B | 594,864 B |

追跡なし側が変更前後で完全に同一であることから、削減が追跡経路だけの
ものであることを確認した。削減 4,032 回（追跡差の約 38%）は、検討 144 件
のうち吸収に至る試行でのオフセット複製（1 試行あたり内部ノード 7 件）
に由来する。確保回数は再測定でも完全に再現した。時間については、
同じハーネスの追跡差が約 2.10ms から約 1.20〜1.59ms と変動の範囲内
であり、時間改善としては主張しない。確保回数の削減が確実な効果である。

## 同一性

- パス単体の印字：上記合成入力について、stash による前後比較で印字全体
  の SHA-256 が一致し、吸収件数も変更前後とも 8 件、検討件数も
  144 件で同一である。
- 公開コンパイル全体：内部ノードを含むオフセットを持つ 1 文の合成入力で
  stash 前後比較を行い、生成コードは SHA-256 一致（140 バイト）、
  勝者は変更前後とも `optimized:function-global/joint-api`、マップの
  mappings・names・sources・sourcesContent・version は同一である。
  `x_storm` の差は `producer.dirty`（測定時の未コミット状態を示す）と
  それを覆う `integrity` のみで、この入力の説明履歴そのものに差は
  出ていない。
- 実データの標準検証：別途用意された real-world コーパス（4,155 件）で、
  変更前後を 4 条件（default / smallest・tolerant・exhaustive・
  zeroCostNewlines:true、各 Map なし／あり）で全件比較した。
  成功／失敗・生成コード・Map 中核・エラー文ハッシュ・正規化済み Map 全体
  （`x_storm.producer` と `x_storm.integrity` を除く）のすべてが完全一致
  し、差分は 0 件だった。すなわち、実コーパスに対しては説明系セクション
  の変化すら観測されなかった。
