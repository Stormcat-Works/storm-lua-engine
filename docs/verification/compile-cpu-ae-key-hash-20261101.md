# コンパイル CPU: ae-reuse 式キーの構成的ハッシュ化＋完全照合（w7 第90サイクル、第251ラウンド）

## 課題

第89サイクルの計装で、ae-reuse（available expression 再利用、26,167 回）の走査 5.87s の最大の葉は式キー文字列構築 `expression_key` の 2.59s（5,310,822 回、総 601,297,056 バイト）だった。本サイクルは (1) その内訳を精密化し、(2) 構成的ハッシュを一次キー＋ヒット時は元の式キーと完全照合する設計が立つかを判定し、立つ場合のみ Tier INVARIANT で実装する。

## (1) 計装精密化（計装専用 worktree、非統合）

std-nomap 全 corpus を逐次単一プロセスで処理するドライバ（corpuscheck の std-nomap 行をバイト単位で再現）で、原子スロット＋スレッド局所キャッシュ方式の低擾乱プローブを当てた。プローブ出力行は無計装 corpuscheck の std-nomap 行とバイト一致。

| 部位 | 回数 | バイト数 | 走査ノード数 | 時間 |
|---|---|---|---|---|
| 照合側キー構築（rewrite_expression） | 4,873,105 | 569,634,673 | 44,154,906 | 1.600s |
| 登録側キー構築（add_candidate） | 437,717 | 31,662,383 | 2,312,531 | 0.099s |
| 合成側キー構築（ae-carriers、本課題の対象外） | 255,180 | 15,575,550 | 930,082 | — |

- 照合＋登録の合計 5,310,822 回／601,297,056 バイトは第89サイクルの記録と完全一致（対象範囲の帰属とプローブ忠実性を数値で確認）。
- HashMap 参照 4,873,105 回に対しヒット 1,526 回（0.031%）。pure 候補の事前参照 136,368 回／ヒット 44 回。登録 437,689 回（登録側構築 437,717 のうち 28 回は pure 長比較の早期 return で終わる）。参照時間 0.142s、登録時間 0.042s。すなわち時間の主体はマップ操作ではなくキー文字列の構築そのもの（1.70s 対 0.18s）で、直接計時 1.70s と第89の葉帰属 2.59s の差は計装方式の会計差。
- キー長分布（全構築部位）: ≤16 が 60,948、≤32 が 584,724、≤64 が 3,054,510、≤128 が 1,226,770、≤256 が 437,342、≤512 が 98,443、≤1024 が 41,833、>1024 が 61,432。平均 113.2 バイト、構築あたり約 8.75 ノード。
- 同一キーの再構築: 照合ヒット率が 0.031% しかないことは、大半の構築が「その場で捨てられる不一致キー」に費やされていることを示す。再訪ノードのメモ化は別途検討したが不採用——保存先（Transformer 単位のキャッシュ）は 26,167 回の生成・破棄を繰り返し、割当 churn が利得（重複走査分のみ）と同程度になる。ハッシュ化は再訪時も初回も文字列構築そのものを消すため、重複度の精密値は設計判定に影響しない。

## (2) 設計判定: 立つ

- ハッシュは `push_node_key` が生成するバイト列そのものを、チャンク境界に依存しない内部ステージング付きでストリーミング計算する（`expression_key_hash`）。キー一致 ⟹ ハッシュ一致は定義により成立する（片方向の要求のみが本質で、逆は照合が担保する）。
- 索引は `HashMap<u64, Vec<AvailableExpression>>`（バケット方式、Fx 系の安価な u64 ハッシャ）。エントリは従来どおり定義ノード `definition: NodeId` を保持するので、照合に必要な情報は常備されている。バケットヒット時は照合側・被照合側の双方の実キーを実体化して比較する——比較器は既存の式キーそのもので、新たな等価性定義を持ち込まない。
- 登録は文字列キー時代の意味論を保存する: バケットが非空なら同一キーのエントリを照合付きで置換し、衝突した別キーは併置する。`retain` はバケット内述語として適用し、空バケットを落とす（述語自体はエントリのフィールドのみに依存し不変）。
- ゆえにハッシュ衝突は余分な文字列比較を生むだけで、誤った再利用には繋がらない。「構築により出力不変」として Tier INVARIANT で実装した。

## 実装（`489b8fc` の分岐元における実装コミット、2 ファイル）

- `passes/immutable_values.rs`: `KeyHasher`（回転＋乗算のストリーミング）と `push_node_key_hash`（`push_node_key` の全分岐をミラー）、`expression_key_hash` を追加。単体テスト2件: (a) 全ノード種を網羅する複数ソースの全ノードについて `expression_key_hash(node) == 実体化キーのバイト列ハッシュ`、(b) 等しいキーは等しいハッシュ（`t.x` と `t["x"]` の同一視を含む）。
- `passes/available_expressions.rs`: `AvailableMap` 型・`KeyIndexHasher`・`find_available`（ハッシュ→バケット→完全照合）を導入し、照合部位・登録部位・`retain`・生成部位を置換。合成側（ae-carriers のキー）は対象外で不変。
