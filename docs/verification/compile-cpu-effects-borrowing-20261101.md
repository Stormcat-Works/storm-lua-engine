# コンパイル CPU: effects 照会の借用化＋single_use_forwarding 呼出内メモ化（w7 第94サイクル、第258ラウンド、Tier FULL）

## 課題

(1) ae-reuse 残部として記録済みの `effects_for_statement`／`effects_for_expr`
（第89計装で文照会 2,404,818 回・0.72s 規模、加えて呼び出し側の所有権都合の
コピー）を、storm-lua-analysis の API 借用化で削減する。API 変更を伴うため
Tier FULL で実施する。(2) api-alias 試行構築の一般形（増分候補化／代数的
測定）は設計のみで、選択一致の証明が立つかを判定する。

## 前提見積もり（決定論カウント、プローブ専用 worktree＋fxprobe ドライバ）

std-nomap 全コーパス（4,155 ファイル）を逐次単一プロセスで処理し、所有形式
ファネル（`statement_effects`／`expr_effects`）の入口で数えた。プローブ行は
分岐元 `b4fef6c` の corpuscheck std-nomap 行とバイト一致（忠実度確認済み）。

- アナライザ生成 786,730 回／文照会 10,959,396 回／式照会 7,980,293 回。
- 文照会の結果要素数: 正規化前 76,376,398 → 正規化後 48,413,228
  （平均 4.42 要素／回、62% が 2 要素以下）。式照会は後 14,115,609 要素。
- 同一アナライザ内での文照会の重複: distinct 5,111,340 件に対し
  repeat 5,848,056 回（53.4%、最大 80 回繰返し）。ただし下記の契約により
  アナライザレベルのメモ化は使えない。

## 前提監査: アナライザレベルのメモ化は契約違反（設計転換）

`crates/storm-lua-analysis/src/effects.rs` のモジュール内コメントは
「mutable summary fixpoint の反復や public な `stable_reads` 設定の変更を
跨いで結果をキャッシュしない」ことを明記し、テスト群は `stable_reads` の
反転や `summaries[i]` の書換（`pub` フィールドへの直接代入）を跨いで
新鮮な結果を期待する。変更チョークポイントは存在しない（第93の
NodeArena のような private＋列挙可能な書換経路とは逆）ため、世代鍵メモ化は
健全に構成できない。よって設計は次の 3 点に転換した:

(a) 借用出力形 API `effects_for_statement_into`／`effects_for_expr_into`
    を追加する。毎回まっさらに計算して呼び出し側の蓄積先へ書く（跨ぎ
    キャッシュは一切しない）ため契約に触れず、呼び出し側はスクラッチを
    再利用して確保を消せる。
(b) 熱い呼出箇所でスクラッチ／プールを再利用する。
(c) メモ化は `single_use_forwarding::collect_plans` の呼出内に限る。
    この間アナライザは `&` 借用で固定され interior mutability を持たない
    ため、呼出内の同一照会は同一結果になる（メモは純粋キャッシュで
    反復されず、順序は観測不能）。メモは呼出とともに破棄される。

## 実装（実装 `76a7c11`＋整形 `51fdc63`／`132b86b`＋clippy 解消 `ce023a0`）

- analysis/effects.rs: `normalize_effects_in_place` を抽出し、借用ファネル
  `statement_effects_into`／`expr_effects_into`（refill → 本体 → 場当たり
  正規化）を新設。所有形式はファネル経由に再実装し、公開借用形 2 本を
  契約明記のドキュメント付きで追加。新規テスト 2 件（全ノード id で
  into == owned（使い回し蓄積先・ゴミ入り初期状態を含む）、公開状態の
  変更（stable_reads 反転＋summary 消去）を into が観測すること）。
- minify 側の転換箇所（全て逐次使用を確認済み）:
  single_use_forwarding（呼出内メモ＋read_follows の二重照会解消＋
  assignment の writes スナップショット化）、available_expressions
  （Transformer の式スクラッチ＋ブロック文スクラッチ）、final_stores
  （rhs プール＋文スクラッチ）、global_stores（rhs プール＋二重照会を
  1 回化＋cleanup_transfer の &Effects 化と式スクラッチ）、captured_use、
  signed_factoring（barrier へのスクラッチ引数追加ほか）、common_offsets、
  scratch_coalescing、default_hoisting、locals、destructive_results
  （merge 用プール）。単発照会の冷たい箇所（screen_buttons、
  sparse_boolean、droppable 系ヘルパ等）は所有形式のまま残した。

## 課題 (2) 設計判定: api-alias 試行構築の一般形は却下

貪欲探索（`run_with_analysis`）の試行は incumbent から ±1 キーの集合で、
受入判定は除去が `len <= best_len`、追加が `len < best_len` のタイ敏感な
比較である。したがって計測の近似は 1 文字の誤差でも選択を変えうる
（出力可視）。正確な代数的測定が立つかは `measure_renamed_size` の構造で決まる:

- rename は全体頻度表ではない。`rename_globals` → `rename_top_locals` →
  スコープごとの再帰割当（`rename_nested_scope`）で、各スコープの局所は
  （頻度降順、宣言順）でソートされ、サブツリー参照集合から決まる禁止名
  （捕捉認識）と生存区間の重なる先行割当のブロックを避けて最短名が
  割り当てられる。
- alias 集合への ±1 は、チャンク全体に生存する根スコープ束縛の追加／
  削除、API 根・メンバの頻度変更、メンバ連鎖ノードの消去を伴い、禁止名
  集合と順位付けを通じて無関係な束縛の名前長まで動かす。反例構造:
  内側関数の局所が現在 1 文字名を得ているところへ、その関数内で参照
  される alias が同名を要求すると当該局所は 2 文字名へ落ち、その頻度分
  だけ増える——この項はキーとそれを参照する全スコープの相互作用で
  決まり、キー単位の統計からは分離できない。
- ゆえに候補の renamed size はキー統計の代数関数では書けない。正確に
  予測するには候補ツリーの resolve とスコープ別割当のシミュレーション
  が必要で、それは構築＋計測そのものの中身である。**代数的測定は却下。**
- 増分構築も採らない: alias 名は選択順の index 由来（`__api{index}`）
  で、途中のキー除去は後続全 alias の改名を招き、interner と全使用箇所
  が非局所に変わる。差分構築器は `apply_alias_set` の第二実装となり、
  選択一致にはアリーナ（値・文字列・起源）のバイト同一性という強い
  同等性証明が要る。集合レベルのメモ化（既存）と第92・93の削減で
  重複側は既に回収済みであり、残る初回構築に対する証明負担と
  リスクに見合わない。将来挑む場合は、候補全数について full 構築との
  アリーナ一致を全コーパスで検証する Tier FULL ゲートが必須条件になる。
