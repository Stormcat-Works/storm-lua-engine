# コンパイル CPU: 親インデックスの密 Vec 化＋temporary_globals ハッシャ監査 — 検証記録

対象: `crates/storm-lua-minify/src/passes/inline_functions.rs`
（`ParentIndex` / `build_parent_index` / `declaration_execution_guaranteed`）
監査対象: `crates/storm-lua-minify/src/passes/temporary_globals.rs`
担当: w7 第86サイクル（軸: std 構成の exhaustive 探索のコンパイル CPU）

## 課題 (1): build_parent_index の密 Vec 化（第83サイクルの残候補 (4)）

第83サイクルで親インデックス構築の共有化（構築 235,010 回 → 55,869 回）を
行ったが、残りの構築自体は HashMap 2 個（`stmt_block` / `block_owner`、
いずれも `HashMap<NodeId, NodeId>`）のままだった。本サイクルで両マップを
NodeId を添字とする密な `Vec<Option<NodeId>>`（アリーナ長）へ置き換えた。
参照側は `ParentIndex::stmt_block(node)` / `block_owner(node)` の
メソッド化し、意味論（保持するキー/値ペアと全ての判定結果）は不変。

なお function_infos 呼び出し・検査候補・構築回数は第83サイクルの
記録（56,420／238,034／55,869）と一致し、計装の忠実性を確認した。

### 検証

- 単体テスト新規 1 件（`parent_index_dense_matches_map_contents`）:
  HashMap で再構築した期待値と密 Vec の参照結果を全 NodeId について
  照合。ワークスペーステストは 1,614 件全通過（第238ラウンド時点の
  1,613＋新規 1）。
- Tier INVARIANT: corpuscheck（4 構成 × 4,155 ファイル、16,620 行）は
  base／head ともソート済み TSV の SHA-256 `743431aa…` でバイト一致
  （FULL-VERIFY-TIP `49d57e3` の記録ハッシュと同一＝累積でも不変、
  fallback 0）。
- clippy: `storm-lua-minify` でエラー 0。fmt: 変更行に指摘なし
  （同一ファイル内の既存ドリフト 1 箇所は base 側のもので本変更と
  無関係のため触れていない）。

### 時間計測（開発ホスト4、MEASURE.lock、submit 1 回・全入力同梱）

208 ファイル（20 件ごと抽出の固定部分集合）の std-nomap コンパイルに
ついてファイル別経過時間の合算を base／head 交互に 3 回:
base 中央値 13,938,437µs（rep: 13,975,706／13,902,114／13,938,437）、

ハッシュ演算・HashMap 構築の消滅に置く。status は全 rep・両側で一致。

## 課題 (2): temporary_globals の SipHash——順序観測可能性の監査（実装なし）

第83サイクルの残候補 (2): `temporary_globals.rs` の整数キー
HashMap/HashSet 群は SipHash の `hash_one` が全体 self の約 11% を占める。
ハッシャ差し替えの前提として、「反復順序が出力（勝者・生成コード・
Map）に観測可能か」を監査した。**本サイクルではハッシャは変更して
いない。**

### コード読みによる切り分け（対象ファイルの全反復箇所）

内容（集合・写像としての値）だけが使われ、順序が結果に届かない箇所:

- `function_bodies` の反復（393 行）→ `loop_involved` は集合の内容のみ。
- `references` の値 Vec は AST 走査順に構築され、キー引きでのみ使用。
- `confined` の所有者集合（424–431 行）は基数の判定（ちょうど 1 つか）
  のみ。
- `relevant_owners`（444–445 行）の反復順で `analyze_block` を回すが、
  `unsafe_bids` は `read_expression` 内で挿入されるだけで解析中は
  読まれず、各所有者の解析は互いに独立。最終内容は和集合で順序不変。
- `intersection`（195 行）・`can_reach`（301 行）・
  `bindings_interfere` の所有者集合反復（513–514 行）は
  帰属/到達可能性の真偽値のみ。DSATUR の saturation（599–605 行）と
  blocked（627–631 行）は色集合の基数と帰属のみ。
- `temporaries`（456–461 行）は使用前に `sort_unstable` で BindingId
  昇順に整列される（484–485 行）。`nodes` の順序は scratch（binding
  順）＋一時変数（昇順）で決定的。
- `slots`（667 行）は相異なる色の基数。

DSATUR の tie-break（第83サイクルで懸念された点）: `options` は
`uncolored`（HashSet）の反復から作られるが（606 行）、`sort_by` の
比較関数は saturation 降順→隣接数降順→freq 降順→**`position`
（決定的な `nodes` 内の位置、全キーで相異なる）の昇順**で終わる
全順序であり、安定ソートへの依存自体が消えている。現行コードでは
tie-break は反復順序に依存しない（TS の挿入順を position で再現する
設計がそのまま効いている）。

順序が内部副作用を持つ唯一の箇所: 色集合の反復（644–646 行）で
`target.strings.fresh("__gs{color}")` を呼ぶため、intern される
SymbolId の割当て順は反復順序で入れ替わりうる。ただし生成コードと
Map は名前を文字列として直列化し（名前プールは出現順構築）、
SymbolId の数値自体は出力に現れない。実験で裏付けた（次項）。

### 実験（異なるシード＝別プロセスでの比較）

- E1（std のシード変動の実在）: `HashSet<usize>`（0..8）と
  `HashMap<u32, u32>`（12 キー）の反復順を別プロセスで 30 回測定し、
  **30 回全て異なる順序**だった。本ツールチェインの RandomState は
  プロセスごとに実際に変動する。
- E2（実パス内での順序変動）: 対象ファイルに環境変数ゲート付きの
  一時計装を入れ（監査後に巻き戻し済み）、合成入力 s1/s3 を
  40 プロセスずつ実行。`relevant_owners` の反復順、DSATUR 初回
  `options` のソート前順序（8–10 要素の置換がほぼ毎回相異なる）、
  色集合の反復順（s3 では 9 要素の置換が毎回相異なる）——いずれも
  プロセスごとに変動することを実パス内で確認した。
- E3（出力の不変性）: 合成入力 3 件（パッキング単独有効化で
  スロット数 5／6／9、所有者・呼出到達・多重代入隣接を含む）を
  40 プロセスずつ、生成コードと Map の SHA-256 で比較し、
  パッキング単独構成・std 構成とも **40/40 全一致**。コーパス全体
  でも corpuscheck の TSV（Map ハッシュを含む 16,620 行）が
  別プロセス間で常時バイト一致していることが蓄積証拠としてある。

### 監査結論

監査した範囲（`temporary_globals.rs` の全反復箇所、合成入力と
コーパス全体のエンドツーエンド出力）では、**反復順序は勝者・
生成コード・Map のいずれにも観測できない**。理由は (i) 反復結果が
集合内容・基数・真偽値としてのみ消費される、(ii) 順序が効きうる
DSATUR 選択は position による全順序 tie-break で固定されている、
(iii) 唯一順序依存の副作用である intern 順は文字列直列化の前段に
留まる、の 3 点による。

### ハッシャ差し替えを実装する場合の前提条件（記録のみ）

- P1: DSATUR の比較関数の全順序性（最終 tie-break = position）を
  壊さないこと。tie-break の除去と同時に行うと観測可能になりうる
  ため、別変更として混ぜない。
- P2: intern 順の SymbolId 割当てが文字列直列化に留まる現行前提が
  続く限り観測不能。将来 Map 形式が名前を SymbolId 順に直列化する
  変更が入る場合は再監査が必要。保険として、差し替えと同一
  ラウンドで色の intern を昇順に固定する 1 行の決定化を併せる
  ことを推奨する。
- P3: 差し替え範囲は本ファイルの整数キー写像（BindingId／ScopeId／
  usize キー）に限り、合格条件は Tier FULL バイト一致＋本監査の
  E3 プロトコル（複数プロセスでの出力比較）の再実施とする。
- P4: 他パスの HashMap 群は本監査の対象外であり、差し替える場合は
  パスごとに同型の監査が前提。
