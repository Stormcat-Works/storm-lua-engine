# constant-argument-specialization の多値最終引数切り詰め（2026-10-30、未公開）

## バグ

constant-argument-specialization パスは、あるパラメータについて全呼出で
同じリテラル引数が渡される場合に、そのパラメータを除去して呼出側の
引数も除去し、パラメータ読取箇所をリテラルで置換する。引数が書かれて
いないパラメータは Lua の nil とみなして特殊化候補にしていたが、呼出の
末尾引数が多値を返す式（呼出または `...`）の場合、書かれていないスロットは
nil ではなく展開値で埋まるため、この推論は誤りだった。次の形で意味が
変わっていた。

- 呼出最終引数：`local function take3(a, b, c) ... end` に対し
  `take3(pair())`（`pair()` は 3 値を返す）と書くと、最適化後は
  `b`・`c` が nil に特殊化され、第2・第3引数が失われた
 （`(7, 8, 9)` が `(7, nil, nil)` になった）。
- 前置引数あり：`take4(0, pair())` でも同様に `c`・`d` が nil 化された。
  この形は safe モードでも発火した（smallest のみではない）。
- vararg 最終引数：`take3(...)` でも同じ穴があった。

発火条件は「特殊化対象の関数が単一箇所（または全呼出で同一形）から
呼ばれ、対象パラメータより後ろの書かれた引数がなく、末尾引数が多値
式であること」。呼出側が local 関数であること（特殊化対象は local 関数
宣言に限る）、および特殊化全体がサイズを縮めることが採用の前提になる。

単独パス無効化スイープ（正本 73 件）で
constant-argument-specialization の無効化でのみ直ることを確認した
（smallest では constant-folding の無効化でも直るが、これは同パスの
積極経路が folding ゲートに依存するためで、犯行は specialization 側）。
なお、スイープの初回は `pass_toggles` を snake_case で送っていたため
ApiCompileOptions（`rename_all = "camelCase"`）に無視され、全パス無効化
でも直らないという誤った結論になっていた。正しいキーは `passToggles`
である。

## 修正

`crates/storm-lua-minify/src/passes/inline_functions.rs` のみ。
`specialize_constant_arguments` の全呼出一致判定（`same`）で、調べる
パラメータ位置がその呼出の書かれた引数列の長さ以上であり、かつ末尾の
書かれた引数が Call または Vararg である場合、その呼出は nil（および
いかなるリテラル）とも一致しないとした。Call と Vararg だけが多値を
返すため、括弧化された呼出（Paren）は 1 値に調整されるものとして従来
どおり nil スロットとして扱う。先頭リテラル引数の正当な特殊化
（`take4(0, pair())` における `a = 0` の除去）は維持され、除去は
パラメータ列と引数列を同数ずつずらすため展開の対応は崩れない。

## 回帰テスト

同ファイルの tests に 4 件追加。うち多値系 3 件は修正前は失敗し、
修正後は成功することを両方向で確認した（多値・前置・vararg）。
残る 1 件は真に欠けた引数（全呼出で nil）の特殊化が引き続き行われる
ことの肯定テストである。なお、多値系のうち素の形 2 件は、パス単体では
サイズゲートに阻まれて修正前でも通ってしまうため、パラメータ名を長く
して単体でも採用される形にしている（前置の形はリテラル特殊化と束ねて
採用されるため、短い名前でも修正前に失敗する）。
