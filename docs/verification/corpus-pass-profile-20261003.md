# Storm Lua Engine v0.3.1 — 実Luaコーパスのパス別性能分析

2026-10-03。Storm Minの保存済み検証コーパス **4,155本**を対象に、現行のv0.3.1開発用ソースを固定して計測した。対象はLua自体のゲーム内実行速度ではなく、**minifyのコンパイル時間**である。最適化パスの実装変更は本調査では行っていない。

## 結果の入口

- 全探索: 成功した対応ペア **4,054本**、通常診断で失敗した対応ペア **94本**。
- 8192目標: 成功 **4,128本**、通常診断で失敗 **27本**。
- 主走査でのハーネス例外は **7入力**。成功例の時間分布へ混ぜず、独立した確認と補完計測を行った。
- 全 **67パス**、**144計測入口**を使用。採用されなかった候補の時間も含む。最初の予備計測は、候補列挙・正規化等の別入口に対する分類を補うため取り直し、最終結果へ混ぜていない。

全統計は `pass-statistics.csv`、`nonpass-statistics.csv`、`aggregate.json` にある。個別入力の記録は `source-statistics.csv`。原文やソースマップ本文は配布データに含めず、SHA-256で入力を識別する。

## 1. 母集団と測定条件

元データは4,155種類、合計11,818,299 UTF-8 bytes。最小0 bytes、最大605,363 bytes、中央値2,059 bytes。車両として採取された原文4,051本、車両以外だけの原文104本を含む。同じ原文の13,737出現や5,966 property条件は別scriptとして数えない。**原文1種類=1票**である。

主集計は `game / smallest / tolerant / zeroCostNewlines:true / exhaustive / runtime properties / targetなし`。比較するのは同じ設定のSource Map OFF/ON。補助集計だけ `targetSize:8192` を指定する。sourceNameは同じ表示名へ固定する。プロジェクトのリンクやLuaの実行はこの測定に含めない。

各script×設定×Map有無を3回実行し、Mapの順を交互にした。**総compile時間が中央値となった実際の1トレース**を各scriptについて採用する。成分ごとに異なる実行の中央値を混ぜず、内訳の合計を保つ。P10/P90は昇順の `(n−1)×p` を線形補間するR7。上下10%の平均は `ceil(n×0.1)` 件の平均であり、P10/P90という境界値とは別である。

WASM初期化・ファイルI/O・計測データの回収・外部 `validateSourceMap` は時間外。マップONには由来追跡、候補評価、必要な内部検査、Source Map v3と理由JSONの生成、通常のWASM境界を含む。GCと短いwarmupは両モードへ同条件で適用する。1プロセスで最大64scriptを処理した後に新しいプロセスへ切り替え、同時に計測するコンパイラは1つとした。

**保存済み車両などのコード群は、開発中の大きな未圧縮ソース群と分布が異なる可能性がある。** このコーパスの頻度を、そのまま全利用者・全開発プロジェクトでの頻度と解釈しない。従来の巨大制御・描画fixtureとも併用する。

### Map追加費用と、少数の遅いscriptへの集中

**全探索**: 合計時間比は **1.386倍**、scriptごとの倍率の中央値は **1.419倍**、P90は **1.631倍**。1.2倍以下は **378/4,054本**。Mapありの遅い上位10%が全体時間の **57.0%**、上位1%が **24.9%**を占めた。

合計時間比は重いscriptの寄与が大きい指標、scriptごとの中央値倍率は1script1票の指標である。両者を取り違えない。これは計測器付きの観測であり、小さな入力の測定誤差も含む。「全入力で最大1.2倍」という開発目標の達成を、この合計比だけで認定しない。

## 3. パス費用の帰属方法

パス呼出全体の時間を **Inclusive** とする。そこから計測された子処理を引いたものが **Self**。改善順位では、共通処理を呼び出し元パスへ帰属させつつ、入れ子の別パスの費用をそのパスへ分けた **帰属費用** を使う。

例えばAPI別名選択の中で名前短縮を呼んだ場合、API別名選択のInclusiveは名前短縮も含むが、帰属費用では別々に数える。**Inclusiveをパス間で足し合わせると二重計上になる。** 共通処理の横断Selfも既に呼出元パスの帰属費用に入るので、そのまま加算しない。パス帰属費用の合計＋パス外のSelf＋WASM境界は総compile時間と一致することを、各測定で検査した。

同じIDのラッパーから本体への入れ子は一重に数える。`periodic-screen-loop-synthesis` は一般的なscreen-loop処理の中の周期候補部分を計測し、周囲の処理と重複させない。`exact-numeric-literal-pooling` は実装上同じトグルに属する表記正規化の入口も含む。

## 7. 8192目標の別集計

このコーパスは実際に保存されたコードが多く、すでに8192文字以下の入力が多い。そこで目標指定の経路だけを計測すると、最適化パスの使用頻度を過小評価する。

Mapなし: 成功4,128本中、実際のsourceチェックポイント返却は4,089本。バイト単位で入力と同じ生成結果は4,089本。両者は定義が異なるため混同しない。

Mapあり: 成功4,128本中、実際のsourceチェックポイント返却は4,089本。バイト単位で入力と同じ生成結果は4,089本。両者は定義が異なるため混同しない。

全67パスと全非パス処理について、この設定の統計もCSV/JSONに別々に保存した。全探索と異なる母集団を混ぜて平均を作っていない。

## 8. 母集団の偏りに対する確認

4,155本は同一バイトの重複を除いた原文であり、正規化された同系統は3,224 familyある。最大familyは299原文。familyは既存コーパスの正規化トークンによる分類で、意味的等価の保証ではない。

`vehicle-only-sensitivity.csv` は車両由来だけの費用を別集計する。`family-weighted-sensitivity.csv` では成功したfamily内の各scriptの重みを均等化して、1family1票にした費用比も示した。`historical-admission-sensitivity.csv` では過去default検証に合格したコホートに限定した費用と使用数を示す。いずれも主集計の置換ではなく、類似コードの量や過去の採否で順位が変わるかを見る補助情報である。

## 11. 次の最適化の選び方

1. 帰属費用の大きいパスを起点に、共通処理の横断Selfと `pass-component-costs.csv` を合わせて調べる。名前解決やサイズ計算が支配する場合は、そのパスの変換本体だけを細かく書き換えるより、同じ候補での重複計算の削減を優先する。
2. 呼出率が高いが変更の記録が少ないパスでは、安価で正確な適用条件の確認が候補になる。ただし記録なしを完全no-opと決めつけず、必要条件を満たさないことをコードで保証する。パスの無効化で速度を作らない。
3. 上位10%だけで費用が膨らむパスは、遅い入力のhashから該当経路を再現して対処する。典型的な小入力の固定費を増やして巨大入力だけを速くしない。
4. Map倍率の改善は、Mapで増えた帰属費用とmap専用の処理を別に追う。通常minifyの高速化と合わせつつ、同じ新実装のMapなしを分母にした1.2倍目標を維持する。

上記はプロファイルを実装判断へ使う原則である。個別の優先順位・効果見込みは、本調査の数値と対象関数を読んだ上で決める。プロファイル結果だけから短縮率や意味的安全性を推定してパスを削除しない。

## 12. 今回の数値から決める具体的な優先順位

**第一優先はAPI別名選択と、そこで繰り返す名前短縮・候補の由来生成。** 全体のMap増分141.312秒のうち、API別名選択は77.314秒、名前短縮は22.018秒。二つで **70.3%** を占める。この二つは帰属を分けているため重複加算していない。

`api_aliases.rs`の`make_candidate()`は、別名集合の試行ごとにASTを書き換え、scope renameを行い、長さを測る。`optimize_api_aliases()`は削除・追加候補を最大4round調べる。そのため単に「最終マップをJSON化する仕事」を速くするより、**不採用の別名集合について由来付きASTを作って捨てる仕事を減らす**方が、今回の分布では優先度が高い。具体案は「構文だけの試行＋同じwinnerの由来付き再適用」や「同一候補上の名前割当・計測の再利用」。選択順・同点規則・最終map全文が一致することを次の実装の受入条件とする。

**第二優先はsingle-use-global-forwardingとequal-scratch-value-coalescingの解析再構築。** 両方の`try_block(ast,root,block)`は、blockごとにroot全体の`resolve`と`EffectAnalyzer::new`を作る。変更がないblockを続けて調べる場合にも同じ全体解析が発生する。コードの変更が成立するまで解析を共有し、成立した時点で破棄する範囲限定の再利用や、正確で安価な候補有無の先行検査が適している。永続的な汎用cacheをいきなり導入する必要はない。

Mapありで、forwardingの帰属費用16.580ms/本のうちEffectAnalyzer構築9.793ms、resolve3.532ms。scratch coalescingの9.848ms/本のうち同6.880msと2.407msだった。変換本体の細部より、**同じ解析を何回やっているか**が主要な改善軸になる。ただし通常経路も速くなるので、Map/非Map比だけでなく絶対時間も別に評価する。

**第三優先は外れ値のblock数・候補数の増加と共通サイズ計測。** Mapあり総時間の上位10%が57.0%、上位1%が24.9%を占める。scratchの中央値は0.697ms/本だが、遅い上位10%平均は87.019ms/本。平均だけを見て典型入力に大きな固定費を追加せず、重いsource hashから再現して対処する。

**以前注目したordered-screen-call-factoringとaffine-wrapper-mergingは、この実コード群では優先度が下がる。** Mapありの平均はそれぞれ0.111ms/本と0.117ms/本、二つ合わせても全体約0.18%。巨大な合成描画fixtureでの重要性は否定しないが、今回の分布ではAPI別名・名前短縮・解析構築より後にする。

**JSON再設計は今回の第一候補ではない。** 最終map.encode全体は平均2.715ms/本、Mapありcompile125.208ms/本の約2.17%。この部分を仮に丸ごとゼロにしても、全体の追加倍率は概算1.386倍から1.356倍までで、1.2倍には届かない。既存のschema1と説明精度を崩して容量だけを削るより、探索中の費用を先に削る。

### 使用頻度の注意点

全体の多くのパスが4,049/4,054本で実際に呼ばれ、残り5本は字句短縮専用の経路だった。したがって「呼ばれるscript数」だけでは優先度の差が付きにくい。主に **累積費用 × 1script内の繰り返し × 条件確認で省ける仕事 × 局所短縮の実績** を組み合わせる。名前短縮は平均約130回/本、EffectAnalyzer構築は約325回/本、名前解決は約671回/本まで積み重なる。

`scope-renaming`や`scratch coalescing`の局所短縮確認数が0でも、未使用や無効果という意味ではない。scope renameはPassResultを返さず、scratchはsaved=Noneでcoalesced件数をdetailに返すため、今回のsize/saved計数では変換実績を網羅しない。PassRecordにもanalysis-onlyのdetailが残る場合があり、「採用経路に記録」も「最終コードを短くした回数」そのものではない。

この調査結果は、直前までの基盤共有化・遅延materialize等の改善と競合しない。候補をどこで何回作っているかという製品側の分布を起点に、既存の共有化を特に有効な場所へ適用していく。
