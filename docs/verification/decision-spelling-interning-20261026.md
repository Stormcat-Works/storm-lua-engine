# 決定理由の綴り共有（2026-10-26、未公開）

`OptimizationReason::decision` が理由ごとに新しく確保していた
code・basis・fact key の `Arc<str>` を、内容が等しい綴り同士で
共有するよう変更した。生成 Lua・候補選択・schema1 のマップ本体・
`x_storm` の説明履歴は維持する。Map 比 1.2 の目標は未達のままで
あり、この変更はその達成を主張しない。

## 原因

決定理由は、書き換えられたノードごとに同じ短い綴り（同じ規則名・
根拠・fact 名）を繰り返し含む。従来は理由ごとに code・basis・
fact key をそれぞれ `Arc<str>` へ変換しており、短い文字列でも
理由あたり 12 回の確保が発生していた。`String` から `Arc<str>` へ
の変換は内容をコピーするため、fact 値の確保とは別に綴りだけでも
無視できない件数になっていた。合成入力 dense-normal の定数畳み
込みでは、480 個の畳み込みノードに対して綴りだけで 5,760 回の
確保が発生していた。

## 変更

`crates/storm-lua-syntax/src/explanation.rs` の `decision` のみ
変更した。公開 API のシグネチャは変えていない。

- code・basis・fact key を、プロセス全体で共有する綴りキャッシュ
  （`OnceLock`＋`Mutex`＋`HashMap<Box<str>, Arc<str>>`）で引く。
  初出の綴りだけを確保し、以後は同じ内容の `Arc<str>` を複製して
  返す。1 回の `decision` 呼び出しではロックを 1 回だけ取得する。
- キャッシュは綴りの内容で引くため、直列化される説明は従来と
  まったく同一である。`Arc<str>` の等価性・ハッシュは内容で決まる
  ため、理由の比較や検証にも影響しない。
- fact 値は共有しない。fact 値はノードごとの観測値であり、共有
  すればキャッシュが入力内容に比例して増え続けるためである。
  fact 値の共有は、メモリ保持とのトレードオフを別途検討する
  候補として残す。

## 測定

合成入力 dense-normal（46,022 バイト）で、VM 2 コア、各条件 31 反復
の中央値。アロケーション計数はハーネス側の計数アロケータによる。

| 測定 | 変更前 | 変更後 |
| --- | ---: | ---: |
| `fold_expressions`（追跡あり） | 約 5.26ms | 約 5.09ms |
| `fold_expressions`（追跡なし） | 約 2.45ms | 約 2.41ms |
| `fold_expressions`（追跡あり−なしの差） | 約 2.81ms | 約 2.68ms |
| `fold_expressions`（追跡あり）の確保回数 | 55,251 回 | 49,491 回 |
| `fold_expressions`（追跡あり）の確保バイト数 | 2,997,942 B | 2,802,102 B |

確保回数の減少 5,760 回は、綴り 12 個 × 畳み込みノード 480 個と
ちょうど一致する。時間の改善は約 0.13〜0.17ms と小さいが、確保
回数で約 10%、確保バイト数で約 6.5% の削減であり、候補ごとに
畳み込みが走る既定 compile では回数分だけ積み上がる。既定
compile 全体の Map 差は測定ごとの変動（約 2ms 以上）が大きく、
この変更単独の寄与としてはパス単体の値を主に見る。

残りの `fold_expressions` の追跡差（約 2.7ms）は、畳み込まれた
ノードごとの書き換え理由・dispositions・fact 値の確保が主体で
ある。fact 値の共有や理由生成の遅延は、出力への影響とメモリ
保持を慎重に見て検討する。

## 検証

- 生成コードは変更前後で同一（SHA-256 一致、10,921 バイト）。
- 公開 API のマップは、変更前後でバイト単位まで同一である
  （SHA-256 一致、2,432,462 バイト）。`x_storm` を含め全項目が
  同一であり、producer・integrity の差も出ていない。
- 対象テスト（syntax・minify・build）と全ワークスペースのテスト、
  `cargo xtask check`・fmt・clippy を通過した。
- なお、初回の対象テスト実行では `storm-lua-minify` のテスト用
  リンクで `undefined hidden symbol` が出たが、依存クレート変更後
  の増分ビルドの陳腐化であり、対象クレートの `cargo clean -p`
  による再ビルドで解消した。ソースの変更によるものではない。
