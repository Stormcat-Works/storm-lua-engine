# 描画レコードの被呼出鎖クローン由来共有による追跡コスト削減（2026-10-27、未公開）

描画レコード詰め込み（`draw-record-packing`）で、詰め込み対象の被呼出
鎖の複製に対する由来付けを共有するよう変更した。生成 Lua・候補選択・
schema1 のマップ本体は維持する。Map 比 1.2 の目標は未達のままであり、
この変更はその達成を主張しない。

## 原因

`NodeArena::derive_from` の高速経路は、対象ノードの値全体が源ノードと
等しい場合にのみ由来スロットを共有する。`copy_callee` は被呼出の
Index・Paren 鎖を再帰複製してから由来付けするため、複製先アリーナで
振り直された子 ID が源とずれ、Index・Paren ノードでは値の等価性が崩れて
低速の書き換え経路（理由の生成・トークン／名前の保持判定・新規スロット
確保）が走っていた。これは区間起点シフト・関数インライン・
common-offset 吸収などで `derive_from_clone` が解消したのと同じ構造で
ある。ただし被呼出鎖は名前・Index 鎖の少数ノードに限られるため、効果は
小さい。

## 変更

- `crates/storm-lua-minify/src/passes/draw_records.rs` のみ変更し、
  `copy_callee` の `derive_from` を `derive_from_clone` に置き換えた。
  複製される被呼出は純粋な複製であり、種類と識別子・リテラルの位置は源と
  同じで子 ID だけが異なるため、`derive_from_clone` の保証に合致する。
  種類が異なる場合や source snapshot を共有しない場合は従来の
  `derive_from` へ委譲する。
- 被呼出の複製本体（Index・Paren 鎖の再帰複製、呼出箇所への設置、後段の
  処理）は従来どおりであり、共有した源スロットが壊れることはない。
  別スコープの注釈が別名にならないよう複製する、という `copy_callee`
  の目的も変わらない。

## 測定

合成入力（`screen.drawText` の繰返し呼出 160 件からなる描画レコード詰め
込み入力。calls=160、helpers=1、saved=3891）。VM 2 コア、測定時 load
average は 1.4〜2.5 程度。計数アロケータ付きハーネスで各条件 31 反復の
中央値を測った。

| 測定 | 変更前 | 変更後 |
| --- | ---: | ---: |
| パス単体・追跡なし確保回数 | 441,452 回 | 441,452 回（不変） |
| パス単体・追跡あり確保回数 | 451,771 回 | 451,659 回 |
| パス単体・追跡あり確保バイト数 | 52,267,858 B | 52,260,434 B |
| パス単体・追跡差（確保回数） | 10,319 回 | 10,207 回 |
| パス単体・追跡差（確保バイト数） | 5,035,452 B | 5,028,028 B |

追跡なし側が変更前後で完全に同一であることから、削減が追跡経路だけの
ものであることを確認した。削減 112 回（追跡差の約 1.1%）・7,424 B は、
詰め込み計画ごとの被呼出鎖ノードに対する低速由来の解消によるもので、
見込みどおり小さい。確保回数・バイト数は再測定でも完全に再現した。
時間については、追跡差が測定ごとに変動したため、時間改善としては主張
しない。確実な効果は確保回数の削減である。

## 同一性

- パス単体の印字：上記合成入力について、stash による前後比較で印字全体
  が SHA-256 一致し、calls=160・helpers=1・saved=3891 も両側同一だった。
- 実データの標準検証：別途用意された real-world コーパス（4,155 件）で、
  変更前後を 4 条件（default / smallest・tolerant・exhaustive・
  zeroCostNewlines:true、各 Map なし／あり）で全件比較した。
  成功／失敗（成功 4,127 / 失敗 28 ファイル）・生成コード・Map 中核・
  エラー文ハッシュはすべて完全一致した。差分が出たのは Map あり条件の
  2 ファイルのみで、いずれも正規化済み Map 全体の説明系セクションのみの
  差分（`x_storm.producer` と `x_storm.integrity` を除く全体の差分で、
  Map 中核には差分なし）であり、冗長な `draw-record-callee-copy`
  書き換え理由の除去という想定内の変化である。欠落行は 0 件で、
  base / head の検証バイナリが異なるものであることも SHA-256 で確認した。
