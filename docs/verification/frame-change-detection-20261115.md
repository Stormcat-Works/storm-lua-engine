# フレームが変わったかどうかの判定方法の測定（2026-11-15）

描画の結果が前回と同じかどうかを、ホストが安く確かめる方法を比べた記録である。エンジンにAPIを足す2つの案を試作して測り、どちらも見送った。

## 背景

エンジンを使うホストの1つは、モニターの画像が前のtickと同じなら送らない。そのために毎tick`frame().copy()`で画素を写し、前回の画素とバイト単位で比べていた。写し取りと比較を省ける手段があるかを調べた。既存の`frame_epoch`は描画のたびに進むので、内容の変化の判定には使えない。

## 比べた方法

| 記号 | 方法 | エンジンの変更 |
|---|---|---|
| A | `copy()`だけ（比較なし。参考値） | なし |
| B | `copy()`のあと、JSのループで前回と1バイトずつ比べる | なし |
| C | `copy()`のあと、`Buffer.compare`で前回と比べる | なし |
| D | `pixels`の借用ビューを`Buffer.compare`で前回の写しと比べ、変わったときだけ`copy()`する | なし |
| E | 寸法と画素の64bitダイジェストをWASMの中で計算して返す（試作） | exportを1つ追加 |
| F | エンジンが前回の問い合わせ時の画素を保持し、厳密に比べて真偽を返す（試作） | exportを1つ追加、VMごとにフレーム1枚ぶんのメモリ |

Eの試作は、非暗号のハッシュである。32バイトを4本の独立した列で8バイトずつ読み、乗算とシフトで混ぜる。割り当ては行わず、外部クレートも使わない。Fの試作は、Rustのスライスの比較と`Vec`への写し取りで書いた。

## 条件

| 項目 | 内容 |
|---|---|
| 対象 | `develop`の`6069666`に試作を当てたruntimeのWASM（release） |
| ビルド | Rust 1.97.1、Emscripten 6.0.6 |
| 実行環境 | Node 26.8.2、macOS、Apple Silicon |
| 描画 | 16本の塗りつぶし矩形、文字列、円を描くスクリプト |
| 集計 | 2,000回までの準備運転のあと、15バッチの平均の中央値。1バッチは32×32と96×96が20,000回、288×160が2,000回 |

A〜Fの表の値は、描画を1回だけ行ったあと、内容が変わらないフレームに対して判定だけを繰り返した時間である。内容が変わる場合の値は、描画と判定を続けて行った時間から、描画だけの時間を引いて求めた。

## 結果

内容が前回と同じとき。単位はマイクロ秒で、1回の判定あたりの時間である。

| 方法 | 32×32（4,096バイト） | 96×96（36,864バイト） | 288×160（184,320バイト） |
|---|---:|---:|---:|
| A `copy()`だけ | 0.62 | 1.41 | 4.79 |
| B `copy()`＋JSのループ | 2.11 | 17.07 | 117.03 |
| C `copy()`＋`Buffer.compare` | 0.57 | 2.47 | 8.58 |
| D `pixels`＋`Buffer.compare` | 0.28 | 0.86 | 3.58 |
| E ダイジェスト | 0.27 | 1.81 | 8.70 |
| F 前回フレームの保持 | 1.01 | 8.87 | 44.31 |

内容が毎回変わるとき。描画の時間を引いた値なので、描画のばらつきを含む。

| 方法 | 32×32 | 96×96 | 288×160 |
|---|---:|---:|---:|
| C `copy()`＋`Buffer.compare` | 0.87 | 3.02 | 7.62 |
| E ダイジェスト | -0.05 | 1.66 | 11.79 |
| F 前回フレームの保持 | 0.31 | 4.79 | 30.19 |

同じスクリプトの描画は、32×32で21.7、96×96で47.0、288×160で154.2マイクロ秒だった。32×32のEが負の値になったのは、差が描画のばらつきより小さいためである。

## 判断

Eは、Bより288×160で約13倍速い。一方で、Aより約1.8倍遅く、Cとほぼ同じで、Dより約2.4倍遅い。Eは「同じ値でも内容が違う可能性」が残るのに対し、Dの結果は厳密である。Fはどの大きさでもCとDより遅く、メモリも増える。

このため、エンジンにAPIは足さず、Dの手順を[例](../../examples/consumer/frame-changes.mjs)として示した。例は`node tools/test-package.mjs`が独立consumerで実行する。

## この測定で言えないこと

- `Buffer.compare`はNodeの機能である。ブラウザのホストはDを使えず、Bに近い比較になる。その場合はEに利点があり得るが、ブラウザでは測っていない。
- 測ったのは1台のmacOS（Apple Silicon）とNode 26.8.2だけである。他のCPU、OS、Nodeの版、ブラウザでは測っていない。
- Eの試作は1種類で、ハッシュの品質の検査はしていない。WASMのSIMDを使う実装も試していない。
- 試作のコードはリポジトリに入れていない。測り直すには、同じ内容の試作を当ててruntimeのWASMをビルドする必要がある。
