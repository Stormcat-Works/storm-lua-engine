# 関数インラインの置換付きクローン由来共有による追跡コスト削減（2026-10-27、未公開）

関数インライン（`inline-functions`）で、置換付きクローンの純粋複製
部分に対する由来付けを共有するよう変更した。生成 Lua・候補選択・
schema1 のマップ本体は維持する。Map 比 1.2 の目標は未達のままであり、
この変更はその達成を主張しない。

## 原因

`NodeArena::derive_from` の高速経路は、対象ノードの値全体が源ノードと
等しい場合にのみ由来スロットを共有する。
`clone_subtree_with_replacements` はパラメータ名の出現箇所を引数の
部分木で置き換えながら本体を複製するため、置換箇所より後ろの子 ID が
ずれ、置換を含まない内部ノードまで値の等価性が崩れて低速の書き換え
経路（理由の生成・トークン／名前の保持判定・新規スロット確保）が
走っていた。これは API 別名パス・単一使用ローカルのシンク・captured
単一使用ホイスト・immutable キャリア合成・common-offset 吸収で
`derive_from_clone` が解消したのと同じ構造である。

## 変更

- `crates/storm-lua-minify/src/passes/inline_functions.rs` のみ変更し、
  `clone_subtree_with_replacements` の純粋複製分岐の `derive_from` を
  `derive_from_clone` に置き換えた。置換分岐は変更していない。置換
  されたノードはパラメータ名のクローンではなく引数の複製であるため、
  従来どおり `relate_from_role` でパラメータ置換の関係を記録する。
- 純粋複製分岐のノードは、種類と識別子・リテラルの位置が源と同じで
  子 ID だけが異なるため、`derive_from_clone` の保証に合致する。
  種類が異なる場合や source snapshot を共有しない場合は従来の
  `derive_from` へ委譲する。
- このヘルパーを使う 3 経路（定数引数の特殊化・リテラル呼出の畳み込み・
  式関数のインライン）はすべて同じ変更の恩恵を受ける。呼出箇所への
  設置（`install_expression`）や後段の処理は従来どおりである。

## 測定

合成入力（`local function f(a,b,c,d) return (a*2+b*3)*(c*4+d*5) end` と
`f(1,2,3,4)` の呼出 500 件、7,947 バイト。本体は 15 ノード・内部 7 件）。
VM 2 コア、測定時 load average は 0.3〜1.4 程度。計数アロケータ付き
ハーネスで各条件 31 反復の中央値を測った。

| 測定 | 変更前 | 変更後 |
| --- | ---: | ---: |
| パス単体・追跡なし確保回数 | 22,144 回 | 22,144 回（不変） |
| パス単体・追跡あり確保回数 | 78,419 回 | 36,419 回 |
| パス単体・追跡あり確保バイト数 | 6,311,317 B | 4,105,817 B |
| パス単体・追跡差（確保回数） | 56,275 回 | 14,275 回 |
| パス単体・追跡差（確保バイト数） | 3,579,924 B | 1,374,424 B |

追跡なし側が変更前後で完全に同一であることから、削減が追跡経路だけの
ものであることを確認した。削減 42,000 回（追跡差の約 75%）は、
500 件 × 15 ノードのクローンに対する低速由来の解消によるもので、
1 ノードあたり約 5.6 回と整合する。確保回数・バイト数は再測定でも
完全に再現した。時間の追跡差も約 8.30ms から約 2.8ms へ縮んだが、
単独パス測定の変動を踏まえ、確実な効果としては確保回数の削減を主に見る。
残りの追跡差 14,275 回は、置換ノード（4 引数 × 500 件）の関係記録・
引数複製経路や、解決・AST 複製の由来コストなどによる。

## 同一性

- パス単体の印字：上記合成入力について、stash による前後比較で印字全体
  の SHA-256 が一致した。収益性のない入力のため保存 0 は両側同一である。
- 収益性のある小入力（`g(x) = x+1` への呼出 20 件）でも、パス単体の印字
  は stash 前後で同一で、保存 35・インライン結果（`r0=3+1` 等）も両側
  同一だった。
- 公開コンパイル全体：インラインが成立する合成入力で stash 前後比較を
  行い、生成コードは SHA-256 一致（51 バイト）、勝者は変更前後とも
  `optimized:root-global/joint-api`、マップの mappings・names・sources・
  sourcesContent・version は同一である。`x_storm` の差は、冗長な
  `function-body-copy` 理由 1 件（`binary:+`、before と after が同一）の
  除去とそれに伴う番号付け替えのみで、由来・処分の span 内容は番号
  付け替えを除いて同一だった。`producer` の差は測定時の未コミット状態を
  示す dirty フラグとそれを覆う `integrity` のみである。
- 実データの標準検証：別途用意された real-world コーパス（4,155 件）で、
  変更前後を 4 条件（default / smallest・tolerant・exhaustive・
  zeroCostNewlines:true、各 Map なし／あり）で全件比較した。
  成功／失敗（成功 4,127 / 失敗 28 ファイル）・生成コード・Map 中核・
  エラー文ハッシュはすべて完全一致し、欠落行は 0 件だった。差分が出た
  のは Map あり条件の 107 ファイルのみで、いずれも正規化済み Map 全体
  の説明系セクションのみの差分（hard 0 件・Map 中核差分 0 件）である。
  抜き出し 1 件の内訳では、除去された理由はすべて before と after が
  同一の `function-body-copy`（`binary:-`・`binary:+`・`binary:%`）で、
  追加された理由はなかった。すなわち、実コーパスに対しても意味・
  生成コード・マップ本体への変化はない。
