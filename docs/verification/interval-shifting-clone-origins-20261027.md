# 区間起点シフトのクローン由来共有による追跡コスト削減（2026-10-27、未公開）

区間起点シフト（`interval-origin-shifting`）で、候補の点・幅・条件の
複製に対する由来付けを共有するよう変更した。生成 Lua・候補選択・
schema1 のマップ本体は維持する。Map 比 1.2 の目標は未達のままであり、
この変更はその達成を主張しない。

## 原因

`NodeArena::derive_from` の高速経路は、対象ノードの値全体が源ノードと
等しい場合にのみ由来スロットを共有する。`clone_subtree` は子を先に複製
してから親を積むため、複製先アリーナで振り直された子 ID が源とずれ、
内部ノードでは値の等価性が崩れて低速の書き換え経路（理由の生成・
トークン／名前の保持判定・新規スロット確保）が走っていた。これは API
別名パス・単一使用ローカルのシンク・captured 単一使用ホイスト・
immutable キャリア合成・common-offset 吸収・関数インラインで
`derive_from_clone` が解消したのと同じ構造である。

## 変更

- `crates/storm-lua-minify/src/passes/interval_shifting.rs` のみ変更し、
  `clone_subtree` の `derive_from` を `derive_from_clone` に置き換えた。
  複製される式は純粋な複製であり、種類と識別子・リテラルの位置は源と
  同じで子 ID だけが異なるため、`derive_from_clone` の保証に合致する。
  種類が異なる場合や source snapshot を共有しない場合は従来の
  `derive_from` へ委譲する。
- 候補の適用本体（シフトした代入・条件の組み立て・起点の由来付け）は
  従来どおりであり、共有した源スロットが壊れることはない（関係の記録は
  スロットをコピーしてから行う）。
- なお、同ファイル内の他の `derive_from`（新たに組み立てる条件・束縛
  などの由来付け）は、対象ノードが源ノードの複製ではないため従来のまま
  である。同じ理由で、同一 AST 内の複製に `finish_rewrite` を使う
  パス（単一使用フォワーディング等）も対象外である。

## 測定

合成入力（`lo`・`p`・`q`・`r`・`s` を引数に持ち、
`(p*2+q*3)>=lo and (p*2+q*3)<=lo+(r*4+s*5)` を返す関数 32 件、2,678 バイト。
点・幅は各 7 ノード）。VM 2 コア、測定時 load average は 0.9〜1.9 程度。
計数アロケータ付きハーネスで各条件 31 反復の中央値を測った。パスは
shifted=4、considered=122（候補評価 122 件）で発動した。

| 測定 | 変更前 | 変更後 |
| --- | ---: | ---: |
| パス単体・追跡なし確保回数 | 133,291 回 | 133,291 回（不変） |
| パス単体・追跡あり確保回数 | 152,786 回 | 144,612 回 |
| パス単体・追跡あり確保バイト数 | 39,702,574 B | 39,283,138 B |
| パス単体・追跡差（確保回数） | 19,495 回 | 11,321 回 |
| パス単体・追跡差（確保バイト数） | 1,361,050 B | 941,614 B |

追跡なし側が変更前後で完全に同一であることから、削減が追跡経路だけの
ものであることを確認した。削減 8,174 回（追跡差の約 42%）は、候補評価
122 件 × 点・幅 14 ノードのクローンに対する低速由来の解消によるもので、
1 ノードあたり約 4.8 回と整合する。確保回数・バイト数は再測定でも
完全に再現した。時間については、追跡なし側の中央値自体が測定ごとに
変動したため、時間改善としては主張しない。確実な効果は確保回数の削減である。

## 同一性

- パス単体の印字：上記合成入力について、stash による前後比較で印字全体
  が一致し、shifted=4・considered=122・saved=12 も両側同一だった。
- 公開コンパイル全体：同合成入力で stash 前後比較を行い、生成コードは
  一致（トップレベルの未使用関数は両側とも除去される）、勝者は変更前後
  とも `optimized:root-global/none`、マップの mappings・names・sources・
  sourcesContent・version は同一である。`x_storm` の理由一覧にも差はなく、
  差が出たのは `producer.dirty`（測定時の未コミット状態を示す）とそれを
  覆う `integrity` のみだった。
- 実データの標準検証：別途用意された real-world コーパス（4,155 件）で、
  変更前後を 4 条件（default / smallest・tolerant・exhaustive・
  zeroCostNewlines:true、各 Map なし／あり）で全件比較した。
  成功／失敗（成功 4,127 / 失敗 28 ファイル）・生成コード・Map 中核・
  エラー文ハッシュ・正規化済み Map 全体（`x_storm.producer` と
  `x_storm.integrity` を除く）のすべてが完全一致し、差分は 0 件だった。
  すなわち、実コーパスに対しては説明系セクションの変化すら観測されなかった。
  両 TSV はバイト同一で、base / head の検証バイナリが異なるものである
  ことも SHA-256 で確認した。
