# literal-call-folding のスクラッチ arena 直接構成による追跡コスト削減（2026-10-29）

## 変更

literal-call-folding パスで、呼出ごとに作られるスクラッチ arena の
構成方法を変更した。従来の `empty_scratch_ast` は
`inherit_ast` と `clone_without_origins` の合成で作っていたが、
`inherit_ast` は源が由来を追跡する場合に空の由来スロット表
（`OriginSlots` の Arc 1 個）を確保し、`clone_without_origins`
がそれを直後に破棄していたため、追跡モードでのみ呼出ごとに
1 回の無駄な確保が発生していた。直接構成ではノード空・由来なしの
arena を最初から作るため、この確保が消える。

- `crates/storm-lua-minify/src/passes/inline_functions.rs`：
  `empty_scratch_ast` を直接構成へ変更した（`NodeArena::default()`＋
  源の strings の clone）。呼出側・利用箇所は不変。
- 回帰テスト 1 件：追跡付き AST から作ったスクラッチ arena が
  ノード 0 件・由来なし・源と同一の文字列集合であることを検証する。

## 等価性の根拠

新旧どちらの構成でも、できあがるスクラッチ arena の状態は同一で
ある：ノード 0 件、源の strings と同一の文字列集合（Interner の
clone は挿入順を保つため SymbolId は同一）、由来表なし。
`inherit_ast` 単独では由来表が残って追跡モードでのみ fold が評価
evidence を構築してしまう罠（第37サイクル相当）があるが、直接構成
では由来表自体が存在しないためこの罠にも当たらない。
`clone_without_origins` 単独では源 arena 全体が残って fold の
resolve が源全体に触れてしまう問題があったが、直接構成では
ノードが空のためこの問題もない。すなわち、スクラッチ上で走る
fold・resolve・測定の入力は新旧で同一であり、最終 AST・由来・
生成コードは変わらない。変わるのは確保回数だけである。

## 残差の分解（本変更の位置付け）

本サイクルの切り分けで、literal-call-folding パスの追跡差
5,134 回（inline.lua、500 呼出）は次のように閉じた：

- パス固定費 3 回（源・対象 clone_ast の過渡スロット Arc と
  tiny arena の空スロット Arc。パス 1 回あたりのため無視できる規模）
- tiny 段階固定費 3 回（tiny arena の初回バッファ・ページ）
- スクラッチ段階 500 回（1 回／件。本変更で除去）
- 直接構成 1,500 回（disposition 1,000 回＋最終スロット Arc 500 回。
  disposition の 1 確保化は件数不変のため第41サイクルで不採用済み。
  最終 Arc はスロット表現のフロア）
- relate 2,000 回（4 回／件。共有ベクタの Arc 置き換えによる
  ベクタバッファ＋Arc ボックス×2 ベクタ。表現フロア）
- context 1,000 回（2 回／件。表現フロア）
- インストール代入段 128 回（IndexMut のスロットクリアによる
  ページ単位 COW：触れたページごとにバッファ＋Arc ボックスの
  2 回。63 ページで約 126 回、7 ページで約 14 回、1 ページで
  2 回と一致。共有設計のフロアであり、代入を避けることは
  できないため本サイクルでは対象外。転送 derive 自体は 0 回で
  あることを転送省略変種で確認済み）

合計 3＋3＋500＋1,500＋2,000＋1,000＋128＝5,134 回で閉じる。
本変更後の追跡差は 4,634 回（−500 回、約 −9.7%）で、
残りはすべて現行表現・現行基盤のフロアである。
