## 問題

`loop_member_reads`（MR）は、書き込まれない基底テーブルについて、
メンバ読みをループ前のヘッダで一度だけ評価して使い回す。ところが
generic-for の暗黙の反復子呼出はこの走査に一切見えない:

- 暗黙呼出は AST の Call ノードではない（Forin ノードの意味論）。
- 反復子本体は Function ノードの内側で、本体走査はそこへ入らない。
- 反復子のフィールド書込み（`t.x = ...` の Index 代入）は、基底の
  名前書込み数にも数えられない。

そのため、基底が plain-table 証明（書込み 0 のローカル基底＋
コンストラクタ初期化＋非 escape、または単一定義グローバル）を
通過すると、反復子が基底のフィールドを書き換えるループでも
ヘッダキャッシュが成立し、2 回目以降の読みが古い値になる。
effects 側の根（Forin の暗黙呼出の効果欠落）は第200ラウンドで
修正済みだが、MR 自身の証明・走査はその情報を一切使っていない
ため、target 現れが残っていた。escape 解析が閉じるのは反復子へ
状態として基底を渡す形（`for v in it, t`）だけで、upvalue として
捕捉する形が穴だった。

さらに外側ループは top-down claiming で本体部分木全体の読みを
claim するため、本体に入れ子の generic-for を含むループの
キャッシュも同じ反復子で汚染される（§回帰ケースの
probe-nested-claim 系）。

## 修正

1. `forin_iterator_bars_header`: プリヘッダキャッシュを使う
   generic-for について、反復子がフィールド書込みフリーである
   ことを要求する。直接既知の関数（書込み 0 の Localfunc、
   単一定義 Funcstat、関数リテラルで初期化されたローカル）だけを
   本体走査の対象とし、本体に危険（フィールド書込み・バリア呼出・
   goto/label・入れ子の generic-for）があればバリア。それ以外
   （呼出結果・パラメータ・再代入された名前・束縛なしの名前）は
   全てバリア。危険走査は基底非依存: 反復子が state 引数・control
   変数・別名経由で到達できる表も保守的に覆うための過剰保守であり、
   entries キャッシュ（body-entry）にも同じ形で効く。
2. 証明済み組み込みイテレータの免除: 反復子式が `pairs`／`ipairs`
   呼出（API エイリアス解決で当該組み込みに解決される場合）または
   bare な `next` 名の場合は免除する。暗黙イテレータは next 系で
   フィールドを書かない。シャドウされた綴りは解決されず免除
   されない。なお、組み込みイテレータの免除が意味を持つのは述語が
   組み込み述語ヘッダ遮断（`is_disqualifying_builtin`、述語側の
   pairs／ipairs 等）とは別系統だからである: pairs 自体はその遮断に
   含まれず、キャッシュ側のゲートに到達する。
3. 外側ループへの伝播（`body_contains_barring_forin`）: 本体部分木
   （Function ノードには入らない、本体走査と同じ可視境界）に
   バリア対象の generic-for を含むループは、プリヘッダ／body-entry
   の両キャッシュを停止する。内側ループ自身の可否判断は不変。

## 再評価条件・残課題

- 危険走査の基底非依存性は過剰保守: 反復子が基底と無関係な表だけを
  書く場合もキャッシュを失う。(base, key) 単位の精密化は機会的
  改善として将来の課題（現行コーパスでは勝者への影響ゼロのため
  優先度は低い）。
- 外側ループへの伝播は「本体にバリア対象 Forin があれば外側全体を
  止める」一律形。位置感応型（Forin より前の読みだけ claim する等）
  は未試行。
- effects サマリとの連携（反復子の書込み先を effects から取得する
  形）は、今回の構文ベースの保守的判定で正確性が閉じたため
  見送った。将来、保守性が実測で問題化した場合の拡張候補。
