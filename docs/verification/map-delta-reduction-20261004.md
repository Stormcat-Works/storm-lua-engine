# v0.3.1 — API別名候補でのSource Map追加時間削減

2026-10-04。**Mapあり/なしの追加時間差を減らす最初の対象として、API別名選択を改善した。** `feat/minify-performance-v0.3.1`を維持し、基盤・計画・実装を別々にcommitした。push・main/releaseへの反映・npm公開は行っていない。

実コーパス全探索の対応成功4,054本では、Map追加時間の合計が変更前比 **66.3%減少**し、Mapありの平均時間が **18.9%短縮**した。Mapあり/なしの合計時間比は **1.387倍 → 1.131倍**。ただし、全コーパスの単一計測は分布を調べる観測であり、最大1.2倍の全件達成とは扱わない。

## 対象と比較元

前回の4,155原文プロファイルでMap追加費用の大きかったAPI別名選択を対象にした。[計画](../design/map-delta-reduction-v031.md)、[元のプロファイル](corpus-pass-profile-20261003.md)。**比較元は公開v0.3.0ではなく、既に基盤の高速化を入れた直前のv0.3.1作業snapshot**である。

基準snapshot: `4124a8e96896cd90d92607ed8e5f51dc353bc0ed88b25f00d1c88db4019c1a7a`。

## 実装内容

旧実装は、別名候補集合を試すごとに元の由来付きASTへAPI別名を適用し、scope rename後の完全ASTを作ってサイズを比較していた。Mapありでは捨てる候補にも位置・理由・名前・関連元の処理が発生する。

新実装は、候補探索の入力を**由来だけを外した、同じNodeId/SymbolId/構文のAST**にする。4-roundの除去/追加順、最大8追加候補、等長候補の扱い、最後の空集合比較、サイズ評価を変えない。採用した別名集合が決まったら、Mapありのときだけ、**元の完全な由来付き入力へ同じ変換を一度適用**し、最終scope renameを行う。Mapなしでは再適用しない。

探索を二重に実行する仕組みではない。最適化パスの無効化・時間打切り・理由情報の省略・schema変更・精度の粗化・最終map生成のAPI外への遅延はない。最終コードとmapは従来どおりcompile呼出の完了前に生成する。

## 計測方法

固定4,155原文について、新旧・Map有無を同じNodeプロセスの独立した無計測WASMで比較した。設定は`game/smallest/tolerant/zeroCostNewlines:true/exhaustive/runtime properties`、全探索と8192目標を分離した。入出力ファイル、初期化、warmup、外部からのvalidate、比較用hash/JSON解析はcompile時間外である。

各variantの実行順を回転し、事前実行とGCを全variantで揃える。**全コーパスは各variant1回**で、反復の厳密な性能認定ではなく全分布と正確性を調べる。別に過去の時間分位点と追加費用の大きい入力から決めた **21原文**を、入力ごとに1回warmupした後 **3反復**して検証した。この部分集合は意図的に重い入力を含み、全コーパスの平均として扱わない。

基準は同じ新実装のMapなし。Mapなしを意図的に遅くして倍率を改善しない。小入力やsource-checkpointの固定費も除外しない。実測は共有開発VMのNode/WASMであり、OS/CPU負荷・JIT等の揺らぎが残る。特に単一sampleの極端な倍率やsub-ms差を保証値と呼ばない。

## 追加の巨大入力と測定のばらつき

実コーパスとは別に、固定した20,275-byteの制御例と129,812-byteの描画例を比較した。初回は同じprocessで新旧×Map有無を回し各3回計測した。描画全探索で新しいMap時間が旧版より長く観測され、target未達と全探索の差も大きかったため、成功した側だけを採用せず、追加で**入力・設定・compiler版ごとに独立したNode process**を使って再確認した。

独立processでは同じmodule warmupと各入力3回の事前実行の後、Mapなし/ありを交互に各7回実行し、その中央値を取った。Map検証済みオブジェクトや、他の版の大きいJSONを計測中に保持しない。初回の値を削除せず、両方を機械記録に残した。共有VMの他作業・JIT・メモリ状態の影響は残り、原因を一つに特定したという意味ではない。

## 正確性と互換性

- 実コーパス8,182成功組で、新旧・Map有無のコード、診断、候補統計、所要時間elapsedMsを除いたPassRecordが一致。mapはproducer/integrityだけを除いて標準部分と詳細x_storm全体が一致した。
- 16,364回の新旧reader交差検証を行った。名前・token・式・文の精度、copy、型付き関連元、理由のbasis/facts、inline文脈、除去/置換を省略していない。
- 固定30入力×8設定=240構成、未達target=0の240比較、新旧map readerの480比較、6つの新旧Worker混成pipeline、通常/LifeBoatの8ビルドも成功。
- 独立した旧API別名アルゴリズムをtest-only参照として残した。全67パスの入力と変換後の入力、JSON復元、shadowing、既存短縮名衝突、Unicode、欠落由来、同点比較、空別名集合を比較し、ASTと完全由来も一致。
- 既存の通常診断失敗121組と、7原文×新旧×Map有無×探索設定=56孤立probeの結果も同じ。全探索trapを成功結果として数えず、今回修正できたとも表現しない。

全コーパスには既存の字句短縮でseparatorがUnknownとなるものが5本あるため、「すべてUnknown 0」とは言わない。変更前後で同じUnknownを維持している。入力Luaを実ゲームへ送り新しく正しさを認定した調査ではなく、コンパイラの変更前後の回帰検証である。

## 残る工程

API別名試行のMap追加費用削減は実装・検証した。次は最大1.2倍を超えるscript、とくにsource-checkpoint/小入力に残るマップ固定費と、最終的に必要な由来生成を分けて改善する。通常経路のblock解析再利用は別の性能軸なので、Map差分の効果と混ぜない。

1.2倍を全条件で保証できるまでv0.3.1の性能対応全体を完了扱いにしない。理由や精度を削る手段、map生成を計測外へ移す手段、mapなしを遅くする手段、既存trapの隠蔽は採用しない。
