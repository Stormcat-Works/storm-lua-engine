# 部分複合レイアウト（S1／MR フル＋SMC partial）の追加（2026-10-30、w4 第78サイクル）

## 変更

target モード限定レイアウトに、S1／MR（フル）の上に SMC の
first-group-only 部分変種を重ねた部分複合レイアウト 4 件を追加した:

- `joint-api-local-s1-smc-partial`
- `joint-api-local-mr-smc-partial`
- `joint-api-local-licm-s1-smc-partial`
- `joint-api-local-licm-mr-smc-partial`

提供条件はフル複合と同じく両パスが発火することに加え、フル複合が
SMC グループを 2 件以上キャッシュした場合のみ（部分変種がフル複合と
異なる場合のみ）。速度順位は部分変種の既存慣例どおり自らのフル複合の
直下に置き、既存レイアウト間の相対順序は不変。
root-local-globalization の polish 適用除外にも 4 レイアウトを追加した。
`layouts_per_job` は 16 から 20 へ引き上げた。
目標なしコンパイルには一切影響しない（レイアウトは target モード
限定経路でのみ構築される）。

## 測定（開発ホスト3、MEASURE.lock、単一 submit ジョブ）

遷移形を再現する合成 tick 入力（base 勝者 licm-mr 178 / head 勝者
licm-mr-smc-partial 186、目標 186。フル複合は 186 を超過）で測定した。

- target コンパイル壁時間（プロセス起動込み、5 対）: 中央値
  base 21ms / head 21ms、対差は ±1ms 以内。変化なし。
- 変更勝者の実行時間（vmbench、200 ticks、21 対の交互測定）:
  1 回目は対中央値 +2.07%（head 高速 10/21 対）、2 回目は +21.51%
  （4/21 対）とばらつきが大きく（head 側中央値だけが跳ね、base は
  両回とも約 6.17µs で安定）、この合成入力では効果はノイズ域と判断
  した。設計上も節約は tick あたり直線読み 1 グループ分（テーブル
  参照 1 回）で、ループ支配の約 6µs に対して小さい。
  開発ホスト2 での参考クロスチェック（高負荷時）では
  対中央値 −5.10%（12/21 対）で、減速の証拠はない。
  実行同一性は両側とも同一出力（Completed、output 一致）を確認した。

## 結論

部分複合は「フル複合が目標を超過し、素の S1／MR に落ちる」ケースで
複合の節約の一部を回収する受け皿であり、コーパス slack32 で 1 件の
実遷移を確認した。余裕のある目標では発火しない（slack128 で 0 件）
ため、コストはタイトな目標を持つファイルの候補評価に限られる。
