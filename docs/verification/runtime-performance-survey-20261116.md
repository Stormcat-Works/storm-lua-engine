# 実行時の性能調査とラスタライザの高速化（2026-11-16）

実行時の経路（VM、Vehicleのバインディング、ラスタライザ、WASM境界）に高速化の余地があるかを調べた記録である。出力を変えない2件をラスタライザへ実装し、契約の変更を伴う候補は測定値を付けて提案に留めた。

## 調べた範囲

| 対象 | 調べた内容 |
|---|---|
| `storm-screen-raster` | 全文を読み、描画命令の種類ごとに測定し、直線はサンプリングプロファイルを取った |
| `storm-lua-vm`の実行経路 | `runner.rs`、`runner/synchronous.rs`、`backend_support.rs`を読み、tickの内訳を測定した |
| `storm-lua-microcontroller` | バインディングとコールバックの入口を読み、Luaの実行とラスタライズを分けて測定した |
| `storm-lua-wasm`、`storm-lua-bridge` | tickとdrawの経路を読んだ。変換と所有権の受け渡しだけで、測定が必要な処理は見つからなかった |

コンパイラとminify（`storm-lua-syntax`、`storm-lua-analysis`、`storm-lua-minify`、`storm-lua-build`）は今回調べていない。これらはv0.3.1とv0.4.0で検証ラウンドを重ねており、記録は[minify性能](../design/minify-performance-v0.3.1.md)と[v0.4.0候補記録](release-candidate-0.4.0.md)にある。TypeScriptのSDKも、tickとdrawの入口を確認しただけである。

## 条件

| 項目 | 内容 |
|---|---|

| ビルド | Rust 1.97.1、release profile、mlua 0.10.5（vendored Lua 5.3） |
| 実行環境 | macOS 27.2.1、Apple M5（arm64） |

どちらのベンチもdebug featureを含めてビルドしている。ブレークポイントとステップは使っていないので、行フックと呼び出しフックは付いていない。値は1台での測定であり、他の環境の性能を保証しない。WASMの値は「検証」の節に分けて書く。

## 変更前の内訳

`runtime_breakdown`は288×160の画面に対して、`onDraw`の実行（描画命令の記録まで）と、記録した命令のラスタライズを分けて測る。単位はマイクロ秒である。

| 入力 | Luaの実行 | ラスタライズ |
|---|---:|---:|
| `drawRectF` 50回（60×40、不透明） | 12.08 | 193.10 |
| `drawRectF` 50回（60×40、alpha 128） | 12.05 | 342.01 |
| `drawCircleF` 50回（半径18） | 11.74 | 172.93 |
| `drawTriangleF` 50回 | 19.44 | 232.40 |
| `drawLine` 100回（画面を横切る斜線） | 24.55 | 363.28 |
| `drawRect` 50回 | 12.02 | 147.40 |
| `drawCircle` 50回 | 11.69 | 116.92 |
| `drawText` 25行 | 6.40 | 24.03 |
| `drawTextBox` 10回 | 4.65 | 17.50 |
| `drawClear` 10回 | 1.36 | 15.19 |

図形を描く入力では、ラスタライズがLuaの実行の10倍以上かかっていた。

tickの値は次のとおりである。

| 入力 | 時間 |
|---|---:|
| 空の`onTick` | 0.29 |
| 2万回の算術ループ | 1839.01 |
| 5千回のループで`math.floor`と`math.sin`を呼ぶ | 959.32 |
| 32チャンネルの入出力（ホスト関数を128回呼ぶ） | 11.31 |

2万回のループは約10万命令なので、1命令あたり約18ナノ秒になる。原因は後述の命令数フックである。

## 実装した変更

2件とも`crates/storm-screen-raster/src/raster.rs`の内部だけを変えた。公開API、ABI、描画命令、期待RGBAは変えていない。

### 塗りつぶしの行スパンをまとめて書く

塗りつぶし矩形、塗りつぶし円、塗りつぶし三角形は、1行ごとに左右の端を求めてから`run`で画素を書く。従来の`run`は1画素ごとに`plot`を呼んでいた。`plot`は座標が有限か、画面内かをf64で毎回調べ、f64から添字を求める。

`run`は呼び出しの時点で行と左右の端のクリップを終えている。そこで、行のスライスを1回だけ取り出し、alphaが255なら色を書き込み、0なら何もせず、それ以外は既存の`blend_pixel`を画素ごとに適用する形にした。左右の端の切り詰めは従来と同じ`as u32`である。

### 直線の画素位置を求める割り算を、整数で計算する

直線は、長い方の軸に沿って1画素進むごとに、もう一方の軸の画素位置を割り算で求める（`floor_div`）。この割り算は、商の小数点以下を負の方向へ切り捨てる。従来はf64の剰余を2回使って計算しており、プロファイルでは直線の時間の約半分が剰余の計算（`fmod`）だった。

直線が渡す値は1/256ピクセル単位の整数値である。割る数と割られる数がどちらも2^52以下の整数値で、割る数が正のとき、従来の式は全段が丸めなしで計算されるので、64bit整数の割り算（`div_euclid`）と同じ商になる。この条件を満たすときだけ整数の割り算を使い、それ以外は従来の式をそのまま使う。割られる数がゼロのときも従来の式で計算し、ゼロの符号を変えない。巨大な座標で代替の丸めに入った値は2^52を超えるので、従来の式で計算される。

## 出力が変わらないことの確認

従来の経路をテスト専用の参照として残し、`raster.rs`の単体テストで比べた。

| テスト | 内容 |
|---|---|
| `fast_paths_match_the_reference_paths` | 7種類の画面寸法（1×1から4096×2、余白つきを含む）で、無作為な命令を1つ適用するたびに全バイトを参照経路と比べる。合計16,800回。命令は色（alphaは0、1、127、128、254、255）、塗りつぶしと輪郭の矩形・円・三角形、直線、`Clear`。座標は画面の内外、小数、境界値、巨大値、NaN、無限大を含む |
| `floor_div_matches_the_reference_bit_for_bit` | 境界値の全組み合わせ484件と、無作為な整数、非整数、負の割る数などの約120万件で、戻り値のビット列を従来の式と比べる |
| `span_fill_writes_opaque_and_blended_pixels` | 塗りつぶしが実際に画素を書くことを、不透明と半透明で確かめる |

比較が働くことは、新しい経路を故意に誤らせて確かめた。行スパンの右端を1画素縮めた場合と、alpha 0の扱いを変えた場合の両方で、1つ目のテストは失敗した。確認のあと元へ戻している。

採用済みの743件のRGBA契約を新しい経路で描いて期待値と比べる検査は、Nativeでは`conformance/tests/raster.rs`（直接の描画命令とLua経由の2経路）、実WASMでは`packages/lua-engine/tests/wasm/engine.test.mjs`（ラスタライザ単体のWASMとLuaのWASM）である。どちらも通過した。`cargo xtask check`と`python3 tools/check_screen_fixtures.py`は契約のファイルとハッシュを検査するもので、ラスタライザは実行しない。

## 実装しなかった候補

### 命令数フックの間隔を広げる（効果は最大、契約の変更が要る）

VMは命令数の上限を数えるために、Luaの命令1つごとにフックを呼ぶ（`runner/synchronous.rs`の`quantum = 1`）。フック1回はmluaの保護つき呼び出しを通るので、Luaの実行時間の大半をこの呼び出しが占める。

`runner/synchronous.rs`の2か所の`quantum`を64に変えた一時的な版を作り、同じ2つのベンチを3回ずつ実行した。「間隔1」はラスタライザの変更を当てた現行の値である。一時的な版は測定のあと破棄した。

| 入力 | ベンチ | 間隔1（現行） | 間隔64 | 比 |
|---|---|---:|---:|---:|
| 2万回の算術ループ | `runtime_breakdown` | 1800.35 | 415.12 | 4.3倍 |
| 関数呼び出しを含むループ | `runtime_breakdown` | 945.09 | 231.07 | 4.1倍 |
| 32チャンネルの入出力 | `runtime_breakdown` | 10.99 | 3.89 | 2.8倍 |
| `drawLine` 100回の`onDraw`の実行 | `runtime_breakdown` | 24.91 | 12.04 | 2.1倍 |
| 空の`onTick` | `runtime_breakdown` | 0.30 | 0.28 | 変化なし |
| `control.lua`のtick | `benchmark` | 0.94 | 0.45 | 2.1倍 |
| `draw96`（実行とラスタライズの合計） | `benchmark` | 76.2 | 41.6 | 1.8倍 |

今回見つけた候補のうち、Luaを多く実行するスクリプトに最も大きく影響する。ただし次の理由で、定数を変えるだけでは採用できない。

1. [architecture](../design/architecture.md)は、入れ子の短いコールバックで未計数の命令がたまらないよう、命令ごとに予算を消費すると定めている。Lua 5.3の`lua_sethook`は呼ぶたびに計数を初期化する（同梱の`ldebug.c`で確認した）。本エンジンはコールバックの開始時と、同期コールバックから戻るたびにフックを付け直す。間隔を広げると、付け直しの間に実行した間隔未満の命令は数えられない。ホスト関数から同期コールバックを呼ぶ処理を繰り返すスクリプトは、上限を超えて動き続けられる。この経路はテストで再現していない。ソースを読んで判断した。
2. 上限に達する命令の位置と、そのとき報告する行が、最大で間隔の分だけずれる。[runtime-host](../specs/runtime-host.md)の位置情報の契約に関わる。
3. 既存の上限のテスト（3,000、2,000、10,000命令）は間隔を変えても通るので、1.の検出には使えない。

採用する場合の案は、フックを付け直すたびに間隔1つ分を先に消費する方法である。数え漏れはなくなるが、同期コールバックを多く呼ぶAddonでは従来より早く上限に達する。採用には、1.を再現するテスト、ADR、architectureの改訂が要る。

### 実装しなかったその他の候補

| 候補 | 測定 | 見送った理由 |
|---|---|---|
| コールバックごとのコルーチン作成とフック設定を使い回す | 空の`onTick`で約0.3マイクロ秒 | 絶対値が小さい。Lua 5.3にはコルーチンを初期化し直すAPIがなく、フックの付け直しはデバッガの契約に関わる |
| 描画バインディングの命令名の比較と引数の`Vec`をなくす | `onDraw`の実行は1呼び出しあたり約0.27マイクロ秒で、その過半は命令数フック | 残りの大半はmluaの引数変換で、名前の比較を除いても差は測定のばらつきに埋もれると見込んだ。試作と測定はしていない |
| 直線の画素ごとの判定（`meets`、`on_segment`）を減らす | 変更後も直線は1画素あたり約6ナノ秒 | 実ゲームに合わせた丸めと端点の規則を持つ経路で、出力を変えずに式を組み替える根拠を今回は用意できなかった |
| 文字と輪郭の`plot`をまとめる | `drawText` 25行で約24マイクロ秒 | 1文字あたりの画素が少なく、効果が小さい |
| SIMD、共有メモリ | 未測定 | [テストと性能計測](../design/testing-performance.md)が、実測と互換性の検証を伴う場合に限ると定めている |

## v0.5.0の準備ブランチでの再確認（2026-11-18）

2026-11-18の時点で`develop`は`33cf347`のままで、本記録の基点から変わっていない。一方、v0.5.0の準備ブランチ`muse/release-v0.5.0`（`23ebb98`、`develop`から30コミット先行）が描画の意味論と実行制限を変えているので、このブランチに本変更を当てて確かめ直した。

### ラスタライザの変更の当たり方

v0.5.0は、円の頂点生成（f32の逐次加算）、`drawText`と`drawTextBox`の文字の扱い、塗りつぶし三角形の頂点の移し方と、743件の契約のうち一部の期待値を変えている。本変更が触れる`run`、`floor_div`、`line`、`convex`の本体は変えていない。`raster.rs`の差分は衝突なく当たった。

塗りつぶし三角形は、従来の行オフセット1から、頂点を移したうえでオフセット0の`convex`を呼ぶ形になった。どちらの形でも行スパンは`run`で書くので、本変更の対象に入る。円の頂点数は8〜16分割のどれでも塗りつぶしで16点以下になり、`convex`の固定長16の配列に収まる。f32の逐次加算を再現して全分割数を確かめた。

| 検査（v0.5.0＋本変更） | 結果 |
|---|---|
| `cargo test -p storm-screen-raster`（従来の経路との全バイト比較を含む3件） | 通過 |
| `cargo test -p storm-lua-conformance --test raster`（v0.5.0の743件の契約、円・文字の新しい検査を含む7件） | 通過 |
| `cargo test --workspace --all-features --locked` | 通過（1,935件、失敗0、無視0） |
| `cargo clippy --workspace --all-targets --all-features --locked -- -D warnings` | 通過 |
| `cargo fmt --all --check` | 通過 |
| 実WASM、3ブラウザ、`cargo xtask check` | 未実施 |

この測定の時点では、`runtime_breakdown`は命令数の上限を1億に設定していた。v0.5.0では`ExecutionLimits::instruction_budget`が`Option`になったので、その行を`Some(...)`へ書き換えて使った。その後、上限を設定せず既定の制限で測る形に改め、`develop`とv0.5.0の両方で同じコードがコンパイルできるようにした。`develop`で全入力が既定の上限（100万命令）に達せず、値も変わらないことを確かめた。

### 命令数フックの間隔

v0.5.0は命令数の上限を既定で無効にし、代わりに1001msの壁時計制限を512命令ごとに確かめる。フックは引き続き1命令ごとに呼ばれ、命令数の上限を設定しない既定の構成でも同じである。間隔を64命令に変えた一時的な版で、同じベンチを3回ずつ実行した。

| 入力 | 間隔1（現行） | 間隔64 | 比 |
|---|---:|---:|---:|
| 2万回の算術ループ | 1824.52 | 411.77 | 4.4倍 |
| 関数呼び出しを含むループ | 970.00 | 232.32 | 4.2倍 |
| 32チャンネルの入出力 | 18.05 | 9.85 | 1.8倍 |
| `control.lua`のtick（`benchmark`） | 1.16 | 0.64 | 1.8倍 |
| `draw96`（`benchmark`） | 76.0 | 40.0 | 1.9倍 |

効果は`develop`での測定と同程度に残る。v0.5.0では、命令数の上限を設定しない構成なら、フックに求められる粒度は時間制限の確認（512命令ごと）だけになる。ただし、フックを付け直すたびにLuaの計数が初期化される点は変わらない。同期コールバックを64命令未満の間隔で呼び続けるループでは、外側のコルーチンでカウントイベントが一度も起きず、時間制限の確認に届かないおそれがある。この経路はソースを読んでの判断で、テストでは再現していない。数え漏れの懸念は、上限を設定しない構成でも時間制限について残る。この候補は2026-11-16の判断どおり実装していない。
