# signed-expression-factoring のキャリア定義による代表出現ノード共有（2026-10-30、ワーカー w9）

## 症状

コーパス e4727bd0 で、最適化構成（opt）でのみ実行時エラー
（vm-error）になった。生成コードが画面高さ由来の式 `y = h/3` の
定義を失い、未代入のグローバルを読む形になっていた。plain／safe
では正常だった。第174ラウンド時点の Tier FULL で base／head が
同一コードを出していた既存バグであり、他の修正とは無関係である。

## 機構

`passes/signed_factoring.rs` の `apply_signed_candidate` が、因数分解
キャリアの定義文（`Node::Local`／`Node::Assign`）の右辺に、代表出現
のノード ID（`group.expression`）をそのまま挿入していた。代表出現の
所属文は書換対象範囲内にあるとは限らない。本件では代表出現は範囲前
の代入文 `y = h/3` の右辺であり、定義文が同じ部分木を参照するため、
その部分木が二重の親を持つ（アリーナが木でなくなる）。

その後 `available-expression-reuse` がキャリア定義文側の親を処理
すると、`h/3` は到達しているキャリア `y` で再利用可能であり、
ノード ID 経由の書換（`rewrite(16, Name(y))`）が両方の親に効いて
`y = h/3` まで `y = y` になった。後段で自己代入が除去され、定義が
失われた。

証拠：パス適用後の AST で、代入文の右辺とキャリア定義文の右辺が
同一 NodeId（16）を指すことをプローブで確認した。新規の合成入力
（範囲前の代入＋後続の繰り返し描画呼出という同形）でも同一に再現
し、同形状を手書きした入力では再利用パス単独では再現しない
（欠陥は因数分解側のノード共有にあることの陰性対照）。

## 修正

キャリア定義文の右辺には、scratch アリーナから複製した fresh な
部分木を使う（`clone_subtree` を追加し、`derive_from_clone` で由来を
接続）。代表ノードは scratch の ID 空間にある（source には存在
しない正規化生成物の場合がある）ため、複製元は source ではなく
scratch とする。`rewrite_signed` の関係付け用引数（relate 先）は
従来どおり代表ノードのまま変えていない。

## 回帰テスト

`passes/signed_factoring.rs` に 2 件追加：

- 因数分解後の木不変条件（全ノードの親が最大 1 つ）＋既存代入
  `y = h/4` が自身の右辺を保持すること。
- 因数分解→利用可能式再利用の合成で `y = y` が生じず
  `y = h/4` が残ること。

いずれも未修正コードで失敗し、修正後に合格することを確認した。
差分実行の合成スイートにも同形の入力（108）を追加した。

## 検証（Tier FULL）

分岐元 15e8e9ea5 対 head でコーパス 4,155 件×4 構成＝16,620 行を
比較した。ステータス変化 0（ok 4,128／error 27 が両側一致）、
Map コア差分 0、生成コード変化は 5 件のみで、いずれも本欠陥の
影響ファイルである：12120577（+16 文字）、b3aa3031（+16）、
e4727bd0（+15）、f1f31d37（+8）、f5cb806b（+9）。合計 +64 文字は
失われていた定義の復元分である。5 件とも差分実行で
plain／opt／safe のトレースが一致することを確認した（f5cb806b は
plain 自体が vm-error の入力で、挙動は同一）。e4727bd0 は opt でも
正常終了し全構成でトレースが一致する。

ワークスペース全テスト合格、cargo fmt／clippy／xtask check 通過。
マージ直前に統合先端が第176〜第179ラウンドで前進したため、リベース
後に累積でも再実施した：FULL-VERIFY-TIP（5d550f9f6）対リベース後
head の変化は同じ 5 件のみ・ステータス変化 0・Map コア差分 0 で、
単体検証と完全一致した。その後第180ラウンドが全行バイト同一で
FULL-VERIFY-TIP を dc47529ca まで前進させたため、累積検証は
この連鎖で閉じる。
