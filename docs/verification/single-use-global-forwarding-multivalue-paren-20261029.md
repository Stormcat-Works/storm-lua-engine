# single-use-global-forwarding の多値展開バグ修正（2026-10-29、未公開）

## バグ

`single-use-global-forwarding` パスが、1 回だけ読まれるグローバルへの
代入式をその使用箇所へ転送する際、Lua の多値調整を崩していた。
ローカル（およびグローバル）に保持される値は常に 1 個へ調整済みだが、
呼出や `...` は多値であり、展開位置（呼出の最終引数・コンストラクタの
最終位置要素・return リスト・多重代入の最終式など）に裸で置くと、
元の 1 個ではなく全値を渡してしまう。

最小再現（既定オプションで発火）：

```lua
local function pair() return 7, 8, 9 end
local a, b = pair()
output.setNumber(1, a)
local x = pair()
local function count(...) local t = {...} return #t end
output.setNumber(2, count(x))
```

修正前は最適化出力が `count(pair())` となり、`count` は 1 個ではなく
3 個の引数を受け取った（差分実行ハーネス diffexec で plain との実行
トレース差として検出）。呼出先が `output.setNumber` のような固定引数
のホスト関数の場合は余剰引数が無視されて表面化しないが、ユーザー定義
の可変長関数では観測可能な意味変化である。

## 原因

2 段の組み合わせで発生した。

1. `root-local-globalization` がルートの `local x = pair()` をグローバル
   代入化し、`single-use-global-forwarding` の対象になった。
2. 転送パスのガードは定義式の `calls` 効果を障壁にしていたが、
   `EffectAnalyzer` は純粋なユーザー関数呼出をサマリ経由で
   `calls=false`・`stable=true` と評価するため、純粋呼出の定義式が
   ガードをすり抜けた。転送先の位置が展開位置かどうかは一切検査
   されていなかった。

## 修正

`crates/storm-lua-minify/src/passes/single_use_forwarding.rs` の
`clone_replacing_reads` を位置認識化した。呼出引数・コンストラクタ
要素・return 値・local/assign の初期化式・汎用 for の反復子式について、
最終スロットだけを展開位置として追跡し（それより深いネストは既に
1 値へ調整されるため対象外）、定義式のトップが呼出または `...` で
かつ使用箇所が展開位置の場合に限り、転送後の式を括弧で囲む。
`(pair())` は常にちょうど 1 値へ調整されるため、ローカルが保持して
いた値と一致する。括弧除去パスは呼出の括弧を保持するため、後段で
剥がされることはない。非展開位置（非最終引数・二項演算の被演算子
など）では従来通り裸で転送し、既存の短縮を維持する。

回帰テスト 3 件を同ファイルに追加した（展開位置の呼出・非展開位置の
呼出・展開位置の `...`）。

## 検証

- 対象クレートおよびワークスペース全件のテストが全成功（新規 3 件含む）。
- `cargo xtask check`・fmt・clippy（syntax・minify lib、警告 0）を通過。
- 差分実行ハーネス diffexec の合成スイート（26 入力×3 構成）で、
  修正前は不一致だった上記の再現入力と 14-varargs が全構成で一致に
  変わったことを確認。
- コーパス検証は Tier FULL（分岐元との全件比較）で実施した。
  4,155 件×4 条件、欠損 0 件、ステータス変化 0 件。生成コードが
  変わった 292 件のうち 265 件は括弧挿入による +2 の倍数の伸びで、
  残る 27 件は勝者再選択による差分だが実行照合で全構成一致し、
  意味変化なしと確認した。詳細は本体 PROGRESS.md の当該ラウンド。

## 残件（次サイクル以降の調査対象）

- 同じ多値調整の family として、単一使用関数の融合
  （`one-use-function-fusion`）による return 位置の展開が未修正で残る。
  再現入力は w9 領域の `diff-inputs/24-sink-return2.lua` にある。
  融合パス側の return 対応を別途切り分けて修正すること。
- 人工的なパス無効化の組み合わせでは、コンストラクタ展開の切り詰め
  （`{pair()}` が `{先頭値}` 化する方向）の候補も観測された。既定
  オプションでの発火は未確認のため、別途切り分けが必要。
