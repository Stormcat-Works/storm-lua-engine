# single-use-local-sinking の多値展開バグ修正（2026-10-29、未公開）

## バグ

`single-use-local-sinking` パスが、1 回だけ読まれるローカルへの定義式を
その使用箇所へ置換する際、Lua の多値調整を崩していた。ローカルに
保持される値は常に 1 個へ調整済みだが、呼出や `...` は多値であり、
展開位置（呼出の最終引数・コンストラクタの最終位置要素・return
リストの最終値・local／assign の最終初期化式・汎用 for の最終反復子式）
に裸で置くと、元の 1 個ではなく全値を渡してしまう。

最小再現（既定オプションで発火。融合を介さない直接形）：

```lua
local function pair() return 7, 8, 9 end
local x = pair()
local c, d = x
output.setNumber(1, c)
output.setNumber(2, d or -1)
```

plain では `c=7`・`d=nil`（出力は 7 と -1）だが、修正前は最適化出力が
`local c, d = pair()` となり、`d=8`（出力は 7 と 8）になった。
第2サイクルの残件だった one-use-function-fusion の return 展開例
（`local x = pair(); return x` をもつ単一使用関数を呼出側へ融合した
`local c, d = wrap()` が `local c, d = pair()` 化するもの）も、融合
そのものではなくこの sinking が後段で中間ローカルを除去した結果で
あり、同じ修正で直る。コンストラクタ形（`local t = {x}` が
`local t = {pair()}` 化して要素数が 1 個から 3 個へ増えるもの）や
呼出最終引数形（可変長関数の受け取る引数個数が変わるもの）も同型で、
同じ修正で直ることを差分実行ハーネスで確認した。直接のコンストラクタ
（`local t = {pair()}`）や直接の return（`return pair()`）は既定
オプションで正しく、別件ではない。

## 原因

2 段の組み合わせで発生した。

1. `single-use-local-sinking` のガードは定義式の `calls` 効果を障壁に
   していたが、`EffectAnalyzer` は純粋なユーザー関数呼出をサマリ経由で
   `calls=false`・`stable=true` と評価するため、純粋呼出の定義式が
   ガードをすり抜けた（前サイクルの single-use-global-forwarding の
   バグと同一のすり抜け）。
2. 置換先の位置が展開位置かどうかは一切検査されていなかった。
   `expand_tree`／`clone_expanded` は木を汎用的にたどって Name を
   置換するだけで、リストの最終要素かどうかを追跡していなかった。

## 修正

置換を位置認識化した（実装は minify クレートの locals.rs のみ＋
回帰テスト 4 件）。`clone_expanded` と `expand_tree` に展開フラグを
通し、各リストノード（呼出・コンストラクタ・return・local／assign・
汎用 for）で最終要素だけを展開位置として再計算する。定義式のトップが
呼出または `...` でかつ使用箇所が展開位置の場合に限り、置換後の式を
括弧で囲むことで常に 1 値へ調整されるようにした。非展開位置では
従来通り裸で置換する。合成した括弧ノードには置換元の Name の由来を
`derive_from` で継承させ、provenance 監査で `(`・`)` が欠落扱いに
ならないようにした（single-use-global-forwarding の括弧と同型の扱い）。

回帰テスト（`passes::locals::inline_tests`）：展開 local への呼出の
括弧化、非展開位置の裸置換、展開 return への呼出の括弧化、展開 local
への `...` の括弧化の 4 件。

## 検証

検証区分は Tier FULL のため、分岐元（第131ラウンド先端 2f8e04a8f）との
全件コーパス比較を実施した（実行前に SHA-256 manifest 照合 4,155/4,155 OK）。
4,155 件×4 条件で欠損 0 件・ステータス変化 0 件（ok 4,127 件・error 28 件
が両側で同一）。生成コードが変わったのは 36 件で、34 件は括弧挿入のみ
（+2 が 25 件、+4 が 9 件、+16 が 1 件で 8 個の括弧）であり、抽出確認した
ものは挿入文字が括弧のみだった。残る 1 件（+5）は勝者再選択によるもので、
base／head 両ビルドの差分実行ハーネスで plain・opt・safe の実行トレースが
全構成一致し、意味変化なしと確認した。写像のみ異なる差分および説明系のみ
の差分は 0 件だった。
