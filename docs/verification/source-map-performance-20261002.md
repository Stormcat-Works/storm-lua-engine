# v0.3.0 Source Map性能の限定改善 — 2026-10-02

**計画を保存してから、理由付きSource Map固有の明白な無駄に絞った1ラウンドを完了した。** 追加の性能追求はv0.3.1以降へ送る。v0.3.0の公開・本番配備は行っていない。

[事前計画](../design/source-map-performance-v0.3.0.md)の保存commitは`96deaec`、性能実装は`31099f1`、追加回帰を含む検証commitは`b57a3a3a9fe4ce4cd9c113e40bf08a0ca251925c`。[機械記録](source-map-performance-20261002.json)。生成Lua、全67パスの由来対応、Source Map v3 + x_storm schema1、理由・関連元・copy・inline文脈・除去/置換記録を維持した。

## 1. 計測から対象を絞った

最初にNativeで最適化本体とmap符号化を分けて測定した。矩形4,096個の例では追跡付きcompile本体が約6.91〜7.44秒、最終map符号化は約0.136〜0.145秒だった。主な時間差はJSON出力だけではなく、探索中に作って捨てる由来情報にあった。

Linux perfも実行したが、hostのperf権限が制限されていたためイベントを取得できなかった。システムの権限設定は変更せず、既存のパスelapsed計測と一時的な工程タイミングを使った。したがって完全なCPUサンプルプロファイルや厳密な割り当て割合を取得したとは表現しない。計測用の分岐は製品コードに残していない。

パス単位の観測例では、追跡付きのscreen-call factoringが約1.413秒、affine wrapper mergingが約0.315秒。今回の修正後は、それぞれ約0.495秒、約0.128秒だった。これは絞り込み用の工程計測であり、全APIの性能比較は下の同条件WASM測定を正本とする。

## 2. 採用した最小限の修正

### サイズ測定だけの名前短縮

試しにscope renameして長さを測り、そのASTを捨てる経路が多数あった。ここでは最終マップに使わない理由・位置情報まで複製し直していた。

追跡有効時だけ、NodeId/SymbolId/構文を変えないsyntax-only複製で同じscope renameとサイズ測定を行う。測定結果の整数だけを返し、この一時ASTを生成物に採用しない。実際に採用する名前短縮には従来の由来付きASTを渡す。非追跡経路は従来の処理を維持する。

### 繰り返し画面呼び出しの部分集合探索

screen.setColor等の共有化では、同じ候補集合・評価順・サイズ判定を維持したまま、捨てる候補の由来構築を省いた。採用する部分集合を決めてから、元の由来付き入力へその変換を一度適用する。

12グループ以下の全組み合わせ、13グループ以上のgreedy、非採用の経路を回帰テストで確認した。最終AST全体を直接の由来付き変換と比較し、理由・関連元・削除記録まで一致することを確認する。探索の候補数を減らして高速化したものではない。

### 定数wrapperの統合候補

平行移動型とaffine型のwrapper統合も、候補の長さを調べる段階だけ追跡を外し、採用した関数ペア・基準引数・向きの変換を元入力に再適用する。採用基準や同長時の順序は変更しない。

複数候補、元の由来が失われた入力、採用後の関連元・除去記録を試験した。元位置が欠けているものを再適用で捏造せず、Unknownのままにする。

## 3. 採用しなかった変更

8.23MBの描画例で、最終origins 13,715件、constructs 20,747件を同値比較したが、そのまま消せる重複はなかった。隣接mapping 27,764件も同じ意味で単純結合できる区間はなかった。理由/関係の表は既に共有されている。

座標変換・標準v3構築・JSON符号化の追加改善は、このラウンドでは探索側ほど大きな効果が見込めないため変更しなかった。mapのフィールド省略、圧縮容器、schema変更、Groupへの粗化は行わない。**mapの生サイズは縮小していない**。性能のために理由や位置を捨てたものではない。

## 4. WASMの変更前後を同条件で再計測

Node.js v22.22.1、同じプロセス内の独立した旧/新WASMを使用。旧版は検査済みP5 tarballのcompiler（source `c851ac3d4f262aa93aae32d3e13b0b3ff397a545`）、新版は本検証commit。旧版と計画保存commitの間でcompiler製品コードに差がないことを確認した。

各入力・条件で両版のmapなし/ありを同回数ウォームアップ後、実行順を入れ替えた5回の中央値を取得した。計測は公開compile呼び出し全体で、mapありには追跡・v3/x_storm・最終JSON化が含まれる。module初期化、読み込み、hash照合、生成後のvalidateは除外し、validateを別に測定する。

Nativeの当初before/after計測もローカルに保存した。測定日・プロセスが離れた結果を、上の同時比較の値に混ぜない。ピークRSSの低下や全入力のメモリ上限は今回測定しておらず、保証しない。

## 5. 出力と理由を削っていないことの検証

同じ代表30入力・240設定で、旧/新map付きの生成Lua、mapなしの生成Lua、候補サイズが一致した。各ソースのSHA-256も元の固定コーパスと照合した。

**Source MapのJSON全体について、実際に変わるproducerとintegrityだけを比較時に除き、それ以外の標準フィールドとx_storm全体が240件すべて一致**した。位置区間・理由のbasis/facts・関連元・精度・copy・inline文脈・削除/置換・設定・候補識別を一部だけ選んで比較したものではない。各本物のmapは正規化前にそのままvalidateし、旧リーダーから新map、新リーダーから旧mapも480回検証した。公開schema1は変更していない。

目標0・fast/beam1の未達240件でも最大探索と生成Lua・origins・mappings・relations・contexts・reasons・dispositions・constructsが一致した。全240設定でUnknownは0バイトを維持する。性能表の巨大入力でも新旧map全体の一致を確認した。

## 6. v0.3.1以降へ送る課題

今回の最小限ラウンドはここで終了する。次の検討対象は、その他の候補に残るsnapshot/metadata複製、最終候補の印字/由来平坦化、schemaの意味を保ったJSON構築・共有表・validatorのメモリ使用量である。必要なprofileを追加し、同じ回帰と比較条件で取り組む。全探索のやり直し、精度低下、理由の省略、map=falseの負担増は改善とみなさない。

現時点でschema1の非互換刷新やバイナリ形式を約束しない。性能改善のために元変数の値/寿命、PC/実列、消えたフレーム等の別機能を抱き合わせない。

## 7. 保存と公開状態
