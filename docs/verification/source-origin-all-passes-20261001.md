## 2. 追加した主な対応

### 引数・テーブル・名前空間

定数引数の特殊化、カラー配列の展開、テーブル引数のscalar化、uniform fillのscalar化、疎なBoolean decode、閉じた名前空間の直接参照化を接続した。元引数と関数内の読み出し、名前付きキーと引用符付きキー、削除後に番号が変わるパラメーター・local slotを区別する。配列の範囲外nilや範囲の重なりを処理するguardにも、元のlookup・境界の由来を付ける。

### 数式と値の共有

interval origin shifting、numeric Boolean/bit特殊化、商と剰余の融合、係数・不変式の共有、積の再結合、共通offsetの吸収、destructive result/radixのhelper化・再利用、scratch valueの統合へ対応した。

共有された保存先を使っても、元の異なる変数や式の出現位置を一つに潰さない。新しい数値は、その値を導いた元の定数・式に対応する。元のオペランドが一部だけ不明なとき、既知の親の範囲や同値の別の出現を根拠に穴埋めしない。

### 描画・出力の圧縮

出力列ループ、screen buttonのhelper化、描画recordの通常・拡張・高密度・共有辞書・規則列の各候補へ対応した。最終的に選択された圧縮方式だけでなく、それぞれを直接呼び出す検証を持つ。

table cell、パレット、符号化payload、辞書展開データ、予測・delta/Rice decoderの初期値を元データに対応させる。デコーダーの制御構造や新しい保存領域はSyntheticと明示する。**元データの初期値まで単にデコーダーだからSyntheticとすることはない。** 実Luaで復号後の値・型・引数数・描画命令順も照合する。

## 3. 完了判定を支えるテスト

**全67パスそれぞれに、実際のproduction entry pointを呼び、コードが変化するfixtureを置いた。** no-opを一回通すだけでは合格しない。

各fixtureでは、追跡ON/OFFのAST・生成Lua一致、通常区切り/改行区切りの2形式、生成位置の検証、ASTのJSON往復、元の由来を消した負例を実行する。全67 IDと台帳・test名の一致もCIで検査する。

さらに全67 fixtureを実コンパイラのsafe/smallest × exact/tolerant × 改行有無へ通す**536設定**を検証した。Unicode/CRLFコメントを加えた原文の位置移動も全67パスで検証する。既存の44ファイルの意味論テストにも、最終出力の由来を検査するadapterを追加した。変換が由来テーブル全体を落としたとき、検証を黙って省略せず失敗する。

分岐別の追加ケースは、shadowing、前後に残る引数、欠けたテーブルキー、引用符付きキー、範囲guard、符号・因子の順序、動的アクセスの拒否、部分的な由来欠落などを含む。圧縮codecではTable/Bytes/PackedBytes/Delta/Rice/Grouped/Prefix等を実Luaで復号し、値・型・引数数・padding・反復時の初期化を照合している。

## 4. 代表240設定の回帰

原文30本のSHA-256が以前の記録と一致することを確認した。safe/smallest、exact/tolerant、改行有無の同じ240設定で、**追跡ON/OFF、変更前後の生成Lua、候補サイズが一致**した。target=0・fast/beam1の未達240比較でも、最大探索との生成Lua・内部由来情報の一致を確認した。

生成491,760バイトのUnknownは**0バイト**。Source 233,460、Derived 245,884、Synthetic 12,416バイトだった。これは位置の精度が全て一文字単位であるという意味ではなく、各区間に記録したprecisionを維持して解釈する。

新旧の実compiler WASMでも240設定と未達30件を比較した。高レベルWASM APIへ追跡optionはまだ公開していないので、これは現行の非追跡APIの回帰であり、未公開のWASM map APIを動かしたという主張ではない。追跡付きWorker転送のJSON/binary契約はNativeで別に検証する。

## 5. 対応関係の目視確認

外部consumer用の小さな実行例から、生成コード・primary・related・名前・precisionをJSONとして出力し、次を確認した。これらは本検証のために作成した公開可能な例である。

| 変換 | 確認した対応 |
| --- | --- |
| 共通の定数引数200を関数内へ移す | 関数内に出た200の主な由来は元の実引数。別の呼び出しにある200と、関数内の元パラメーター参照は関連元として別々に残る |
| `bits&256>0`を`bits>>8&1`へ変換 | 新しい8や1は元のmask・比較値から導いた値。bits参照は元の識別子位置を保持する |
| `module['long-key']`を短いscalarへ変換 | 引用符付きキーの元リテラル範囲に対応する。元に書かれていないidentifier名を捏造しない。新しい保存領域はSynthetic |

生の対応関係は機械記録のmanualExamplesにも残した。無関係な文・ファイル・近い行を選んで位置を埋める処理は加えていない。

## 7. 残る工程と境界

**P3の「全最適化パスへの由来対応」は完了。** 任意の壊れた/部分的な由来テーブルを正確なmapへ修復する機能ではなく、その入力ではUnknownを返す。Source/Derivedにも名前・式・文・処理群の精度があり、Syntheticも含まれるため、Unknownが0であることと一文字対一文字の一致は異なる。

次の製品上の工程は、P4の標準Source Map v3・詳細由来公開型、リンク前の元ファイルへの合成、Rust/WASM/TS境界、code/map/source snapshotの組み違い防止。続くP5はPlaygroundの双方向選択、関連由来、生成/不明の表示、実行環境が返す位置との接続である。最適化で消えた変数やstack frame、特定の描画loop反復の復元は位置マップとは別機能。

実装は既存の`feat/minify-source-provenance-v0.3`へcommit・push済み。本検証記録も同じブランチへ保存する。main、release、公開済みv0.2.1のタグ・配布物・本番サービスは今回の変更対象ではない。実行ログ・私有入力・旧新の生成Lua・再現用ハーネスはリポジトリ内の`local-validation/source-provenance-030-all-passes/`へ保存し、公開文書には集計と公開可能な例だけを残す。
