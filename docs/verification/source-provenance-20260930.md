# ソース位置追跡 P0/P1 実装・検証記録

記録日: 2026-09-30。対象は`d4bcfbf`から分岐した`feat/optimized-source-maps`の未コミット変更。公開済みv0.2.0の差し替え、タグ、push、他ブランチへの反映は行っていない。

[設計と残りの計画](../design/source-provenance.md) / [機械可読の計測・検証データ](source-provenance-20260930.json)

## 1. 到達点

**P0（target未達時の探索共通化）とP1（非短縮buildの詳細な位置対応）を実装・検証した。** 最適化ASTの由来保持、最終minifyソースマップ、Playground表示はP2〜P5に残る。`minify`と`build(minify:true)`は引き続き最適化後mapを返さない。

原文のlintは元位置を返し、リンク後の診断は詳細なコピー範囲から元モジュールへ変換する。lintそのものに生成コードがなければ、.mapを毎回生成する必要はない。

## 2. target探索の変更

旧経路はsource/baseを試した後、cheap/balanced用のASTを別々に最適化し、目標未達ならbaseから通常のコア最適化と全候補評価をやり直していた。

新経路はsource/baseの早期達成を維持し、それ以降を通常のコア・重複除去済み候補と共有する。コーディネータが評価した候補は`SearchContext.completed_batches`へ保存し、Workerには残りの候補だけを渡す。完了結果は同じ候補集合と同じsize/order規則で選ぶ。候補の逐次・逆順完了、コンテキストとジョブのシリアライズ往復も試験した。

壁時計時間は測定値として扱うだけで、打ち切り・候補選択には使用しない。全探索を意図的に遅くしたり、未達時に探索品質を落としたりして差を合わせていない。

原文候補のサイズ報告がUTF-8バイト数になっていた箇所をUTF-16単位へ統一した。また、最後の一意候補まで評価して目標を達成した場合は、完了を`stoppedEarly:true`と誤報しない。

### 最終WASMの再測定

Intel Core i5-13400F上のLinux/KVM、Node v22.22.1。releaseビルドのWASMを明示的に初期化し、`minify`呼び出しだけを計測。初期化、ファイル入出力、hash計算、生成Luaの実行は含めない。小さな入力で一度warm-upし、同一入力での事前warm-upは行っていない。13万・26万文字と制御サンプルは3回の中央値、52万文字のストレス入力は1回。実WASMだがブラウザの時間計測ではない。

| 入力 | 変更前の8192未達 | 最終版の全探索 | 最終版の8192未達 | 未達/全探索 |
| --- | ---: | ---: | ---: | ---: |
| 129,812文字 / 4096矩形 | 10.08秒 | 3.26秒 | 3.17秒 | 0.97倍 |
| 259,607文字 / 8192矩形 | 33.09秒 | 11.02秒 | 10.11秒 | 0.92倍 |
| 519,201文字 / 16384矩形 | 135.03秒 | 36.47秒 | 32.53秒 | 0.89倍 |

全件で`mode:smallest`、`searchMode:exhaustive`、`zeroCostNewlines:true`、既定のtolerant数値モード。同じ条件に`targetSize:8192`を付けたものを比較した。矩形入力は合成の画像変換風コードで、短縮後は34,084 / 67,352 / 133,744文字となり目標未達である。

変更前の列は直前に同じVMで再測定した旧WASMの値。最終版は別プロセスで再測定したため、プロセスの履歴・JIT・allocator・CPU状態による差を含む。「未達の方が本質的に速い」「すべての入力で同じ時間」という結論にはしない。重要なのは、旧来の二重・三重処理を除去し、同じ候補集合の評価を一度ずつ行う構造へ変えたことである。

全探索の生成Luaは変更前・変更後でhash一致。未達の矩形入力では全探索/8192未達の両方もhash一致した。最終成果物のWASM SHA-256は`50c27e041273d0f69d6aceb33ec16d728fd8275e1138d2bb39af9703b47f6213`。

### 同一プロセス内での交互比較

最終メタデータ修正前の候補WASMと旧WASMを独立したインスタンスとして同じプロセスにロードし、版の順序を交互にして比較した。ここでもコア/候補探索の共通化は同じ実装である。変更後WASMは`001b152864bc667e47f6daeb5446fc5f147c646690045bc01095c38b618ce767`。この比較後、最後の候補での完了フラグを修正し、上記最終WASMを再ビルド・再試験・再測定した。

| 入力 | 変更前: 全探索 / 未達 | 交互比較の変更後: 全探索 / 未達 |
| --- | ---: | ---: |
| draw-4096 | 3.85 / 10.08秒 | 3.38 / 3.40秒 |
| draw-8192 | 11.20 / 33.09秒 | 11.03 / 10.43秒 |
| draw-16384 | 59.01 / 135.03秒 | 47.83 / 48.62秒 |

単発の以前のベンチマークとは絶対時間が異なるため、以前の値を今回の同時比較値と取り違えない。全サンプル、処理CPU時間、入力/出力hash、実行順はJSONへ保存した。

### 目標を達成する実用的な入力

20,195文字の既存制御サンプルでは、変更前の8192目標中央値は0.324秒、最終版は0.335秒。早期終了の出力は7,958文字から7,748文字へ変わった。全探索は最終版3.089秒で、出力5,706文字は変更前と一致する。

cheap/balancedの独立した経路をなくしたため、目標達成時に選ぶ候補は以前と同一とは限らず、すべての達成入力の高速化を約束しない。source/baseによる達成、および一部の候補評価だけでの達成は引き続き早期終了する。

「現実的な範囲でおおむね4秒以内」は実用的な既存サンプル等の観測として維持する。任意の巨大入力への上限ではなく、4秒で探索を止める設定は追加していない。以前の大量文字列テーブル代入P-01の長時間処理は今回個別に解消・再測定していない。

### Nativeの初期確認

P0実装後のreleaseバイナリでは、4,096矩形は全探索3.797秒 / 未達3.702秒、8,192矩形は12.672秒 / 13.159秒。単発測定で、最終完了フラグ修正前のもの。これを最終WASMの値と混ぜない。

## 3. 詳細な非短縮ソースマップ

`LinkedRange`に生成側の半開バイト範囲と元ソース開始オフセットを追加した。原文コピー時に記録し、最終文字列の差分から推測しない。通常リンクとLifeBoatの両方を対象にした。

syntaxの`LineIndex`を共有し、UTF-8バイト位置、Lua診断の1-based行/バイト列、Source Mapの0-based行/UTF-16列を変換する。長い一行でトークンごとに行頭から再走査しないよう、改行と非ASCII文字の幅差を索引化する。

標準mapはトークン開始、行頭、コピー区間境界にアンカーを出す。内部のコピー範囲は正確なバイト対応だが、標準mapの任意のトークン内部位置は直前のアンカーへ解決する。文字ごとの完全な対応とは説明しない。

合成された宣言・return前置コード・loader・EOFは明示的にunmappedとする。LifeBoatの開発専用ブロック、不要section、除去したdirectiveは、除去した時点で範囲を記録して元位置から差し引く。Unicodeを空白に置換してバイト数を維持しただけの区間に、原文の対応を残さない。

リンク後の診断も同じ範囲で元モジュール・列・終端へ戻す。終端が別の原文区間や合成コードをまたぐ場合は終端を省略し、無関係な位置に近寄せない。`names`は空で、最適化後の変数対応は未実装である。

## 4. 手動で確認した対応

自己完結したUnicode/CRLFの2ファイル例で、実際の生成Luaと独立したtrace-mapping consumerの結果を確認した。行は1-based、列は0-based UTF-16である。

| 生成位置 | 実際の対応 |
| --- | --- |
| 4行22列の`function()` | `lib.lua` 1行7列 |
| 同じ4行の0列にある合成代入prefix | 元位置なし |
| 5行21列の`return 7` | `lib.lua` 2行21列 |
| 10行18列の`output.setNumber` | `main.lua` 1行59列 |

`lib.lua`の原文は`return function()`から始まる。生成物は同じ行に`__stormmin_link_lib = `を追加するため、元の関数と合成代入を区別する必要がある。main側も同じ原文行にrequireとcallbackがあるため、行だけの対応では足りない。対応表・生成コードはローカルの`manual-map.json`へ保存した。

ソースコードのレビューでは、target未達時のコア最適化が一経路であること、評価済みjobを残りへ再投入しないこと、全探索の候補採否とtie-breakを維持することを追跡した。各種AST置換への由来引き継ぎはまだ実装していない。

動的な時間上限をユニットテストの合否条件にせず、重複job不在、候補集合・出力の同一性、シリアライズ往復を回帰ゲートにした。性能は別の実測として残す。

## 6. 互換性と残りの工程

低レベルRustの`LinkedRange`を直接初期化するコードには新しいbyte範囲フィールドが必要となる。Workerのopaqueな`SearchContext`シリアライズ形式も評価済みbatchを含む。同じ版のcompilerインスタンス間の一時データとして使用し、旧バイナリのcontextを新バイナリへ混ぜる前提にしない。

一般的なTS build/minify結果の公開型とSource Mapのversion=3は維持する。ただし、従来の「常にcolumn=0」では合成prefix上の原文を特定できない。実行位置が行しかなければ、その行の由来を列挙して一意/曖昧/生成専用を区別する。

P2〜P5として、Parser/Printerと由来サイドテーブル、最適化パスの引き継ぎ、最終minify mapの公開API、Playgroundの双方向表示を残す。元変数やインラインフレームの完全復元、VMの命令/列位置、高度な反復ごとの由来は別のデバッグ機能である。
