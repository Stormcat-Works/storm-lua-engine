# テーブル引数スカラ化にパラメータ予算チェックが無く、200 上限の関数が読込不能コードを生成した（2026-10-31、未公開）

## バグ

w6 第52サイクル（Codex 指摘 #7 系「ローカル挿入パスに予算チェックなし」クラスの完結監査）で発見。テーブル引数スカラ化（`table-parameter-scalarization`）は、テーブル引数をキーごとの個別引数へ置き換える際、置換後のパラメータ総数を確認していなかった。パラメータは同時有効ローカルとして数えられるため、引数 196 の関数で 5 キーのテーブル引数を展開すると引数が 201 になり、生成コードが VM に読込を拒否された。再現（c52-probes/c11b-paramscalar-nc）: plain は正常、opt／safe／target32／target128 の全てが vm-error。引数 195 の対照（c12b-paramscalar-nc、展開後ちょうど 200）は全構成一致した。パラメータはグローバル化できないため救済も効かない。

## 原因箇所

`crates/storm-lua-minify/src/passes/tables.rs` のテーブル引数スカラ化。第208・212〜215ラウンドで他の挿入パスへ入った予算チェックが、このパスには入っていなかった。同クラスの 8 例目。なおスカラ化の候補は通常関数のみで、メソッドは候補にならない（メソッド呼び出し側を書き換えないため）ので、暗黙の `self` の加算は不要で明示引数の数で正確に判定できる。

## 修正

- 候補ごとに、置換後のパラメータ総数（現引数数 − 1 + テーブルのキー数）が `MAX_LOCALS`（200）を超える場合はスカラ化をスキップする。
- 回帰テスト 2 件を追加: 196 引数＋5 キーでスキップ／195 引数＋5 キー（ちょうど 200）で発火。

## 検証

- ワークスペーステスト全通過（1,536 件、本ラウンド分は tables の 2 件）。
- 再現 c11b-paramscalar-nc は全 5 構成で正常終了・トレース一致に転じ、c12b-paramscalar-nc の対照ではスカラ化が維持された。
- Tier FULL（base `ac159f045` = FULL-VERIFY-TIP → head、実世界コーパス 4,155 件 × 4 条件 = 16,620 行、開発ホスト1）: base／head の corpuscheck TSV がバイト単位で完全一致（SHA-256 `e88ee2b4…`、両側とも success 4,128／error 27 × 4 条件）。上限近傍での発火抑制のみのため、コーパスへの影響ゼロは設計どおり。回帰 0 件。
