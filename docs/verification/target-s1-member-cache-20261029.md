# target モードでのループ内単発メンバ呼出キャッシュ S1（2026-10-29、未公開）

## 背景と判断
- 第56サイクルで、ループ内同一メンバ呼出の関数値キャッシュ（M2 形・
  ループ内2回以上）は、勝者コードが既にメンバ・エイリアスによる
  チャンク・レベルの local 呼出になっているため、コーパス全件で
  生成コード不変としてマージ見送りとなった。
- 第57サイクルのセンサスで、ループ内1回・ファイル内1回の S1 形は
  メンバ・エイリアスに包含されない（単発はエイリアス選択の対象に
  ならない）ため、勝者コード上に非 LICM 2,791 グループ／1,356
  ファイルが残ることを確認し、本サイクルを実装サイクルとした。
- 本変更は target 限定である。目標なしの最高圧縮とは混ぜない。
  予算の判定は既存の over-target 降格に任せ、S1 専用の文字数
  ゲートは置かない。

## 変更内容（`storm-lua-minify` のみ）
- 新規 `passes/single_member_cache.rs`：
  `cache_single_member_calls_post_alias`。第56サイクルの証明機構を
  そのまま流用する（builtin ルート未変異、単一定義エイリアス基底
  の証明（多シンボル local の初期化子不足に対する `exprs.get` 修正
  を含む）、未知呼出・メソッド呼出・状態付き builtin・表書込み・
  goto のバリア、関数内呼出の除外、最外ループによる claiming）。
  変更点は対象条件のみ：ループ本体内でちょうど1回のグループだけを
  キャッシュし、2回以上の M2 形は放置する。ループ外の出現は
  キャッシュを妨げない（ループごとに独立の preheader を作る）。
- `passes/mod.rs` へのモジュール登録のみ。パス ID の新規登録は
  しない（LICM と同じレイアウト変換の扱い。`effectivePassToggles`
  に項目が増えず、勝たなかったファイルの map は churn しない）。
- `search.rs` の target 限定レイアウト追加：
  `joint-api-local` の直後に `joint-api-local-s1`、
  `joint-api-local-licm` の直後に `joint-api-local-licm-s1` を、
  キャッシュが発火した場合のみ追加する。速度順位は
  licm-s1 > licm > local-s1 > local > joint-api > その他。
  描画後 polish の root-local-globalization 除外に S1 レイアウト
  2 件を追加した。
- キャッシュ局所名は、プログラムの文字列集合に存在しない最短の
  1 文字識別子を使う（全文字が埋まっている場合のみ生成名へ
  フォールバック）。第56サイクル形の生成名 `__membercache` は
  レイアウト候補では scope renaming が短縮せず、合成入力
  （s1draw3、headroom 24）で S1 候補が 217 文字になっていたのが、
  短縮名で 193 文字（local 版 183 文字に対し +10 文字）に改善
  した。文字列集合に存在しない名前はユーザーコードから宣言・
  参照され得ないためシャドウしない。後にキャッシュされる
  グループは、先に intern された名前を避けて次の文字を取る。

## target モードのコーパス差分（各ファイルの目標なし勝者サイズ＋slack を目標）
- 目標なし側は全 slack で完全同一（free_ok・free_size・free_layout
  の不一致 0 件）。失敗 28 件は両側で不変。
- slack +32：遷移 506 ファイル（local→local-s1 499 件、
  licm→licm-s1 7 件）。サイズ合計 +6,863 文字（最小 +4・最大
  +32）。target_met の反転 0 件、予算超過 0 件。
- slack +64：遷移 496 ファイル（490 件・6 件）。サイズ合計
  +6,948 文字（最小 +4・最大 +40）。反転・超過 0 件。
- slack +128：遷移 140 ファイル（134 件・6 件）。サイズ合計
  +1,976 文字（最小 +4・最大 +104）。反転・超過 0 件。
- slack が大きいほど遷移が減るのは、ベース段階のチェックポイント
  （`none` 候補）が目標を満たして早期復帰し、フルサーチに到達
  しない OBJ-2 の既定挙動による。S1 の効果は予算が浅い場合に
  集中する。旧命名（`__membercache`）での +32 は 473 ファイル／
  +4,735 文字だったため、短縮名は捕捉率とサイズの両方を改善した。

## 実行速度の確認（計測専用マシン 開発ホスト3、MEASURE.lock 経由）
- 合成入力 s1draw3（headroom 24）の base／head 勝者ペア：
  base は `joint-api-local` 183 文字、head は
  `joint-api-local-s1` 193 文字で、差分は S1 変換のみ
  （preheader `local d=c.drawRectF` と呼出の local 化）。
  .ud での実行同一性：両勝者とも Completed、出力スナップショット
  同一、描画コマンド 131 件で一致（壁時間は主張に使わない）。
- .us 確認（交互・21 反復、20 draws／反復、ウォームアップ 20、
  開始・終了時 loadavg ともに 0.17 の低負荷。同一マシン内の
  相対差のみ）：base 中央値 97.791 µs/draw → head 中央値
  96.532 µs/draw、ペア相対差の中央値 −1.24%、head が速い対は
  13/21。別途の 1 回目もペア中央値 −0.80%・13/21 対で同方向。
  効果は小さくノイズを含むため、定量主張は「約 −1%・方向は
  モデル通り」に留める。命令数モデルでは反復あたり GETTABLE
  1 命令の節約（128 反復で 128 命令／draw）であり、壁時間の
  方向と整合する。

## 既知の限定
- S1 レイアウトが勝てるのは、フルサーチに到達し、かつ S1 候補が
  目標内に収まる場合に限る。ベース段階のチェックポイントが目標を
  満たす入力では、S1 レイアウトは生成されない（OBJ-2 の既定挙動）。
- LICM との結合レイアウトの勝者は slack によらず 6〜7 ファイルと
  少ない。LICM がホイストする呼出の callee はループ外に出るため、
  S1 との重なり自体が小さい。
