# VM 方言変換: 多重代入の last-wins 化と末尾ラベル goto の受理（2026-10-31、ワーカー w9）

ユーザー判断（2026-10-31、判断事項2）により、storm-lua-vm の2件を本プロジェクトの
基準意味論（Lua 5.3）に合わせて修正した。対象は storm-lua-vm クレートのみで、
コンパイラ（minify／analysis）には触れていない。

## 症状

(a) 多重代入の重複ターゲットが first-wins になる。`d,m,d = 1,2,3` に対し VM は
d=1 を返すが、基準意味論は last-wins で d=3。w9 第11〜12サイクルで、分類済み
TRACE-DIFF 35 件中 7 件の単独原因と特定されていた。実測では代入文は全ターゲット種
（グローバル／ローカル／upvalue／テーブルフィールド／添字）で first-wins であり、
ローカル宣言文だけが last-wins で、文の種類により挙動が割れていた。

(b) ローカル宣言を飛び越えて同一ブロック内のラベルへ跳ぶ goto が load 時に拒否
される（`jumps into the scope of local`）。ラベルがブロックの本当に最後にある形は
受理されるため、ラベルの後に文が続く形（w6 第39サイクルの h1／v10 形）だけが
不整合に拒否されていた。当該プログラムは Lua 5.3 の void 文スコープ規則
（ラベルは void 文であり、ローカルのスコープはその手前で終わる）により正当。
なおシステムの PUC Lua 5.4 でも同形は拒否されることを確認しており、目標は
PUC の実装挙動ではなく本プロジェクトが採用した方言規則である。

## 機構

VM バックエンドは mlua 0.10.5 の vendored PUC Lua 5.3 で、(a) は PUC が多重代入の
ストアを逆順に行う実装、(b) は PUC の goto スコープ検査が「ラベルの後に文がある
場合はラベルの位置で交差ローカルが活性」とみなす実装に由来する。いずれも
mlua／PUC 本体には手を入れず、ロード時のソース変換で等価形へ書き換えることで
是正した。

## 修正

新モジュール `crates/storm-lua-vm/src/dialect.rs` の `rewrite` を、ユーザーソースの
load 経路2か所（`Vm::execute` と require ローダ）に適用する。変換はトークン列
ベースで保守的に行い、構造を確信できない箇所があれば変換せず元のソースを返す。
改行は追加・削除しないため行番号は保存される。

- (a) 重複ターゲットを含む代入文について、ターゲット式と右辺を出現順に一時
  ローカル（チャンク内で未使用の名前を選ぶ）へ評価してから出現順にストアする
  形へ書き換える。評価順（ターゲット式→右辺、全式を先に評価）と最終値
  （last-wins）が基準意味論どおりになる。置換末尾には空文を置く: minified
  コードでは呼出で終わる代入文の直後に区切りなしで次の文が続く形があり、
  一時変数名と後続識別子の結合を防ぐ（後述の回帰で検出）。
- (b) 交差したローカルがラベル以降（入れ子コードと repeat の until 式を含む）
  で一切参照されない場合に限り、最初に交差するローカル宣言からラベル直前までの
  区間を `do ... end` で包み、ラベルを元のブロックに残す。ラベル後に交差ローカル
  への参照がある形は変換せず、従来どおり load エラーになる。

## 検証

- 回帰テスト 21 件を dialect に追加（(a): グローバル／ローカル／テーブル／
  添字／upvalue の重複 last-wins、RHS 評価順保存、swap、宣言文不変、重複なし文は
  無変換、区切りなし後続形。(b): h1 形・ラベル後 return・v10 形・ローカル2つ・
  repeat 本体・ブロック末尾・後方 goto の受理と、ラベル後参照／捕捉／until 参照の
  拒否継続）。ワークスペース全件 1,517 件合格・失敗 0（統合先端 d45e6b2f8 への
  リベース後の木）、fmt／clippy（自変更分）クリーン、xtask check 通過。
- vmprobe（diffexec と同一の oracle 構成）: (a) 全形が last-wins 化し RHS 順序と
  swap は不変。(b) 従来拒否されていた正例が受理に転じ、ラベル後参照形は従来
  どおり load エラー。
- Tier FULL（corpuscheck、4,155 ファイル×4 条件）: 分岐元 7d38fbfbc に対しても、
  統合先端 d45e6b2f8（FULL-VERIFY-TIP）に対しても、全条件 identical=4,155、
  hard／core／expl／missing 0、ステータス ok 4,128／error 27 で不変。
  コンパイラ出力（生成コード＋Map）は変わらない。
- diffexec 分類への影響（全コーパス 5 構成、base VM vs head VM）: 初回測定で
  c5513735 が全構成 vm-error 化する回帰を検出した（上記 (a) の識別子結合が原因。
  空文の追加で修正し回帰テスト化）。修正後の再測定では状態変化 0 件、分類遷移は
  自己不安定ファイル（dcff9f53／4f689f31、pairs 順序ノイズ）の反転のみで、
  決定論的な分類変化はゼロ。第11〜12サイクルの対象 7 件は、5 件が現行ベース
  ライン時点で既に全構成 MATCH、残り 2 件が同ノイズ族であり、「VM 起因
  first-wins」の分類クラスは現行ベースラインには存在しない。変換の発火実績は
  原典 3 ファイル・opt 出力 2 ファイル（いずれも観測窓内ではトレース差なし）。
  (b) の発火はコーパス内に 0 件で、受理範囲の拡大による新たな乖離はない。
